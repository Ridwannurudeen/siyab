# Account investigations and team workspaces

This document describes the implemented configuration and its limits. Service files are operational templates; their presence does not establish that a particular release is deployed or that a worker is running.

## Browser and shared work

The existing browser workspace remains usable without an account. It keeps investigations, graph view settings, notes, watchlists and optional browser notifications on that device. Local monitoring checks the current feed window while a Siyab page stays open. Display pause controls remain separate from alert monitoring.

The save dialog defaults to **This browser**. Signing in does not upload local data. Choose a team explicitly to save a shared investigation, or review and confirm an import from browser storage or a JSON file. Imports create records without replacing existing notes; identical title, notes and URL triples are skipped. Import time becomes the shared record's creation time. Original browser data and backup files remain unchanged.

Cloud backups can contain up to 500 investigations and 100 watched accounts per team. The browser-only workspace has its existing 50-investigation limit, so a larger shared backup cannot be imported there as a whole. Shared file imports are bounded to 8 MiB and sent in batches of at most 50 investigations and 24 KiB; progress reports completed batches. After an interrupted response, refresh before retrying the same backup, because a timed-out request may have committed. Exact duplicates are skipped on retry.

Shared investigations use versions. If another editor saves first, a stale update or deletion is rejected. The editor preserves the draft and offers a draft download and an explicit reload of the latest version.

## Accounts and permissions

Accounts use a 3 to 40 character lowercase username and a 12 to 128 character password. Passwords use salted scrypt hashes. Sessions expire after seven days and use HttpOnly, SameSite=Strict cookies, with Secure cookies on the production HTTPS origin. Session tokens are not returned to browser JavaScript or stored in browser storage. Authenticated changes require the configured exact Origin and a CSRF token.

Registration, password changes and recovery show a recovery code once. Keep it privately; it can replace a forgotten password. Password changes and recovery revoke other sessions and the previous recovery code. Email password reset is not configured. Losing both the password and recovery code has no self-service recovery path.

| Role | Permissions |
| --- | --- |
| Viewer | Read and export team investigations, watches, alerts and audit entries |
| Editor | Viewer permissions plus save/edit/delete investigations, manage watched accounts, import and acknowledge alerts |
| Owner | Editor permissions plus invitations, member removal and role changes |

Invitations are single-use codes bound to an existing recipient username. They expire after 24 hours and initially grant viewer or editor access. Owners can subsequently change roles; the last owner cannot be removed or demoted. An account can belong to at most 20 teams. Application audit entries record team changes but are not tamper-proof against server administrators.

## Public data and source bounds

Global search links valid mainnet account identifiers to `/investigate.html?account=<account>`, while retaining recorded account/entity matches. Testnet accounts are outside this view. A missing recorded match does not establish a favorable payment result.

Mainnet profile, holdings, transaction and transfer reads expose RPC/indexer sources and unavailable states. Holdings metadata is read from token contracts; names, symbols and decimals are contract-reported. Contract source metadata and links are also reported values, not verified ownership or reproducible source-code matches. Validator observations apply to the returned epoch. Labels retain their own provenance and uncertainty.

Live flow/relationship graphs read at most six accounts and 20 transfers per account. Edges establish observed transfer relationships within those windows, not common ownership. Public observations and immutable graph evidence can be retained in the account history database. Private team notes, credentials and watchlist ownership do not belong in those public artifacts. The same database holds the transfer events that watch polling records for team inboxes, and those are not public: an event id is a hash of public transfer fields, so `/live/account-events/` answers 404 for every id, and a team member opens an event from the team inbox at `/workspace-api/teams/<team>/events/<id>`, which serves it only to members of a team whose inbox holds it and otherwise answers exactly as for an unknown id.

Transaction and transfer backfills read one or two provider pages per request, up to 100 rows per page. The shared archive allows one backfill call per account per minute across transaction/transfer kinds. Public backfills and investigation job reads have separate global provider page budgets, 12 pages per minute in all. A public backfill reserves its one or two pages up front and is accepted only while that minute's public count stays within 4 pages (`intel/history.py:PUBLIC_BACKFILL_PAGES`). Investigation jobs of all teams together read at most 8 pages per minute (`intel/history.py:JOB_BACKFILL_PAGES`). Neither count includes the other, so anonymous backfills never take pages from investigation jobs and job reads never close the public backfill route. Watch polling uses neither budget. Continuations must match the archive's committed cursor; concurrent backfills for an account are refused. Public backfills keep their cursors in at most 10,000 account and kind checkpoints; a backfill for a new account and kind that finds all 10,000 kept first removes one that holds no lease and whose minute has passed, an exhausted one before others and otherwise the one least recently advanced, together with its lease row, and is refused only when none can be removed, so the removed account's next backfill starts over without a cursor from its newest page while the pages and rows already archived for it stay (`intel/history.py:AccountHistory.backfill_account`). Archive browsing reads already retained rows; it does not fetch all account history automatically. An exhausted provider cursor still reports `history_complete: false`. Rate limits, provider omissions, polling gaps and history preceding the available pages can remain.

History schema version 2 tracks archive budgets: 128 MiB of retained document/row bodies, 10,000 provider pages, 100,000 history rows, 2,000 graphs, 100,000 event observations and 200,000 watch-deduplication entries. Capacity is shared across accounts. Anonymous public reads stop adding to a budget once it is 75 percent full; watch polling and investigation jobs can keep writing pages, rows, bytes, events and watch-deduplication entries into the remaining quarter, except that pages, rows and graphs stop at 112 MiB of bytes, as described below (`intel/history.py:PUBLIC_ARCHIVE_PERCENT`). Graph snapshots are written only by public graph reads, so they stop at 1,500, the public share of the graph budget, and later graph reads answer without a snapshot; an investigation job keeps its graph with the job and does not archive it as a graph snapshot. A profile, transaction or transfer read whose rows are all retained already, unchanged apart from their observation times, request hashes and read block, adds no page: it cites a retained page that holds every row, or each row's own retained page when no single page does. Transaction and transfer reads are windows of the account's history, so only the rows are compared, and a read holding a subset of retained rows, or differing only in its pagination, source or coverage, adds no page either; a profile read is one row, so a profile whose source or coverage differs adds a page. An empty transaction or transfer read that matches the latest retained page apart from its page size adds none either. A holdings read is a window of the full token inventory: it adds no page only when the newest retained holdings page for the same offset and page size holds exactly the same tokens, none missing and none added, each unchanged apart from observation times, request hashes and read block, with the same inventory total and next offset, and an empty holdings read adds none only when that newest page is empty too. A token that has gone from or been added to that window, or a changed inventory total or next offset, therefore adds a page while the archive has capacity. When a limit is reached, new observations are refused or paused while retained evidence remains available, with two exceptions for watch polling. When recording a new transfer event would pass the 100,000 event budget or the byte budget, the poll first removes delivered events, those the workspace database already holds, oldest first by the time each was recorded, until the new event fits both, in the same transaction, and releases their count and bytes from the budget. An event not yet delivered is never removed, so when removing every delivered event would still not make room the poll is refused, removes nothing and is retried later (`intel/history.py:AccountHistory.poll_watches`). Watch deduplication keeps at most 1,000 entries per account (`intel/history.py:MAX_ACCOUNT_WATCH_SEEN`), five times the 200 transfers one poll reads, and a new entry past that removes the account's oldest entries first by insertion order; a new entry at the 200,000 entry budget removes the oldest entries of any account first by insertion order (`intel/history.py:MAX_WATCH_SEEN`). Both happen in the same transaction and release the entries from the budget. These removals are silent: no audit entry records them. A removed event keeps its team inbox evidence link: the workspace database keeps its own copy of every event a team inbox links to, and the team event route serves that copy only when it reproduces the exact bytes whose SHA-256 is the event id, and otherwise answers 404 as for an unknown id. A removed deduplication entry never raises a duplicate alert or adds a second inbox row for a transfer. The workspace database records each event id once, and it also keeps each transfer event's transfer identity, a hash of the event without its transaction hash, block height and block timestamp, so it is fixed by exactly the receipt, transfer index, asset, sender, receiver and amount that deduplication compares. A transfer event whose identity it already holds resolves to the event already raised and adds no event and no inbox row, even when the provider later reports that transfer with a different or newly known transaction hash or block (`intel/workspace.py:SQLiteWorkspaceStore.ingest_event`). Opening a workspace database written before this identity existed adds it to every retained event in place, in short resumable batches that finish before the store is used, retrying briefly when another process holds the write lock; an event whose stored JSON cannot be read keeps its body and gets an identity that matches no transfer (`intel/workspace.py:SQLiteWorkspaceStore`). An entry removed at the 200,000 entry budget can still be among a quiet account's latest 200 transfers. That account's next poll then records those transfers again and can read a second page and mark a coverage gap, and a transfer that arrived after the watch was added but before its first poll can then reach the team inbox once, as a late alert. Nothing removes archived pages or history rows. When the page, row or byte budget cannot take a transfer page a watch poll reads, the poll still records that page's deduplication entries and raises and delivers its alerts as above, and it does not archive that page: the page's rows are missing from archive browsing for that account, and the poll marks that account's coverage gap, counted in `coverage_gap_accounts`, so the account's coverage reads incomplete (`intel/history.py:AccountHistory.poll_watches`). The same happens when a page holds a transfer that is already archived but now comes back with a different timestamp: the archived evidence is never overwritten, the page is not archived, the account's coverage gap is marked, and new transfers on that page still raise their alerts once (`intel/history.py:HistoryConflictError`). Each event names its own source, the provider and receipt id, so it does not depend on an archived page. Of the 128 MiB byte budget, 16 MiB is kept for events (`intel/history.py:EVENT_ARCHIVE_BYTES`): a page, history row or graph that adds bytes is refused when total retained bodies, including events, would pass 112 MiB, while a new event is admitted when total retained bodies including that event stay within 128 MiB or retained event bodies including that event stay within 16 MiB (`intel/history.py:AccountHistory._reserve`), so with the byte budget full of pages and rows new events still have 16 MiB of their own once delivered events are removed as above, and only undelivered events filling that room refuse the poll. Delivered events that use bytes below 112 MiB leave pages that much less room until they are removed. An archive written by the previous release can already hold more than 112 MiB and up to 128 MiB of pages, rows and graphs; these are retained unchanged and its events still get their own 16 MiB, so the code allows up to 144 MiB of retained bodies in that database, while an archive written since stays within 128 MiB. The byte budget measures retained bodies, not the entire SQLite file or its WAL/index overhead. Each history database connection that writes sets `PRAGMA max_page_count=131072`, allowing a 512 MiB database file at 4 KiB per page (`intel/history.py:AccountHistory._connection`); this file limit is separate from the retained-body budgets and does not include WAL sidecar files.

Before the archive reuses, cites or returns a retained history page, history row or portfolio observation, it checks that a page or observation hashes to its id, that each record is canonical JSON of the expected mainnet shape and that a history row is held by the retained page it cites. The history and portfolio databases are written only by Siyab, so these checks guard against damage to a record, not against someone who can rewrite a database and its hashes; keep the state directory private as described below. A damaged record is never reused or cited, archive browsing that would return or cite it answers 503, and a fresh read of the same history rows replaces a damaged history row. Portfolio observations are never replaced. A damaged history row that no later read covers, and a damaged portfolio observation, keep archive browsing that reaches them for that account and kind at 503 until an operator repairs them.

## State and services

Use one external state directory for the API and all workers. The service templates use:

| Purpose | Path |
| --- | --- |
| Checkout and generated pages | `/opt/siyab` and `/opt/siyab/demo/site` |
| Environment file | `/etc/shieldbot-near/env` |
| Shared state directory | `/var/lib/shieldbot-near/siyab` |
| Accounts, teams, cases, watches, inbox and audit | `workspace.sqlite3` in the state directory |
| Public account observations and graph evidence, team inbox transfer events and polling progress | `history.sqlite3` in the state directory |
| Retained-feed indexing progress and retry leases | `monitor.sqlite3` in the state directory |
| Private queued investigation requests and progress | `investigation-jobs.sqlite3` in the state directory |
| Public immutable portfolio observations | `portfolio.sqlite3` in the state directory |
| Entity source recheck state | `entity-sources.sqlite3` in the state directory |

The state directory must be outside the source checkout and generated site. The service user is `shieldbot-near`; give that user ownership of the directory, mode 0700, and keep database/backup files private. SQLite databases use WAL, so sidecar files may exist. Do not publish the state directory as a static asset or copy it into a release archive.

`FASTNEAR_API_KEY_FILE` names a provider credential file outside the repository. Its contents must be readable by the service user without being placed in command arguments, browser code or logs. It is sent only with a configured provider budget database, never by the feed follower. `SIYAB_PROVIDER_BUDGET_DB` overrides the shared `provider-budget.sqlite3` in the state directory; keep it outside the checkout and generated site. The hosted verdict leaves its account-age fallback disabled unless `SIYAB_VERDICT_NEARBLOCKS=1`. `FEED_STATE_DIR` names the existing external feed state directory; the retained-feed monitor reads its `events` subdirectory. The account reader also uses the configured mainnet RPC endpoint where applicable. Keep existing environment names and deployed contract identifiers unchanged.

The service commands are:

```sh
python -m intel serve --host 127.0.0.1 --port 8792 --site demo/site --live --state-dir /var/lib/shieldbot-near/siyab --workspace-origin https://siyab.xyz
python -m intel monitor --state-dir /var/lib/shieldbot-near/siyab
python -m intel history-follow --state-dir /var/lib/shieldbot-near/siyab
python -m intel investigation-follow --state-dir /var/lib/shieldbot-near/siyab
python -m intel delivery-follow --state-dir /var/lib/shieldbot-near/siyab
```

Use `--once` on a worker for a bounded pass. That flag does not drain all work. The API requires `--state-dir` for shared workspaces and durable observations; `--live` enables live account reads. An explicit localhost HTTP workspace origin is supported for local development; production uses the exact HTTPS origin.

After release review, install the matching API, monitor, history, investigation and delivery templates from `deploy/` in systemd. They use the external environment file and shared state directory, restart on failure, run without root, and restrict filesystem writes to that directory. Create the state directory before starting them. The monitor reads local feed evidence; the other services need outbound provider access. API, history, investigation and delivery units load the optional `siyab-provider.conf` override after the base environment. API and delivery also load optional `siyab-delivery.conf` containing the `SIYAB_TELEGRAM_TOKEN_FILE` path. Keep credentials outside releases and restart both token-using services after rotating the token.

The reverse proxy must send `/workspace-api/` and `/live/` to the loopback API while preserving their paths. Do not cache workspace responses. Overwrite `X-Forwarded-For` with the actual client address rather than passing client-supplied values through, because rate limits use that address behind a loopback proxy. Keep the public site origin aligned with `--workspace-origin`.

## Worker coverage and limits

The workers serve different sources; one healthy heartbeat does not establish that the other worker is healthy. When a tick of the investigation worker meets a storage error, such as a full disk, the worker writes the error name to its service log and tries again after its polling interval instead of exiting; with `--once` it exits with the error. The history worker records a storage error, such as a full database, that meets a watch tick while it claims or polls a watched account as its `last_error` and keeps its heartbeat; an error that escapes the tick is written to its service log and the worker tries again after its polling interval, while with `--once` it exits with that error (`intel/history.py:AccountHistory.poll_watches`, `intel/history.py:run`).

- The retained-feed monitor indexes existing evidence files in bounded batches of 200. Initial retained files are backfill candidates; they do not represent newly observed external deliveries. Missing or unreadable evidence remains visible in retry/coverage status.
- Ordinary-transfer polling handles at most one watched account per five-second global tick. A successfully polled account is not due again for at least 60 seconds. Each account poll reads at most two pages of 100 transfers within a 20-second provider deadline. Larger watchlists, provider latency and retries increase revisit time. The watched account list is compared with retained polling and deduplication accounts in memory, and stale accounts are removed with one account bound per execution; it is never bound into one SQL statement, so the number of watched accounts is not limited by SQLite's variable limit (`intel/history.py:AccountHistory.poll_watches`).
- Initial ordinary-transfer observations seed archive rows and deduplication state without enqueueing historical inbox events; the one exception is a deduplication entry removed at the 200,000 entry budget, described with the archive budgets above. Later unseen rows can enter matching team inboxes. If the previous anchor is not found within the bounded pages, the account records a coverage gap. A running process does not clear that gap or establish complete event recovery.
- Monitor status exposes retained-feed health separately from `account_polling`, including heartbeat, last successful poll, initialized accounts, retries, gaps, backfills and pending event delivery. An empty inbox does not establish absence of activity or risk.

Telegram is the first external delivery channel. The dedicated bot is `@siyabonnearbot`. A team owner starts an expiring, single-use link, opens it in a private Telegram chat, then explicitly confirms the observed account in the workspace. Entering an arbitrary chat ID cannot activate delivery. Missing credentials, wrong bot identity or an existing webhook prevent worker delivery. The worker never removes another webhook. Only new eligible alerts after confirmation are queued; historical candidates and private investigation notes are excluded. Disconnect cancels queued deliveries, but an already in-flight request may finish. Delivery is at least once: an uncertain provider acknowledgement can cause a duplicate. Failed deliveries retry with bounded attempts and provider cooldowns, then remain available as dead letters for owner retry until retention prunes them. Binding, queue and attempt state are included in the workspace database backup. Email and user-configured webhooks are not integrated.

A connected destination belongs to the owner who started its link. Removing that member from the team, or changing their role from owner to editor or viewer, disconnects the destination in the same transaction as the membership change: a pending link stops working, queued deliveries are cancelled and the audit log records `telegram.disconnected` with the affected member. An already in-flight request may still finish. Changes to other members leave the destination connected, and the same member's destinations in other teams are unaffected. Destinations connected before links recorded their starting owner have no linking user. They are disconnected conservatively when any member of that team is removed or any owner of that team loses the owner role, and otherwise keep delivering until an owner connects them again, which records that owner. Opening an existing database adds the linking user column in place; existing rows stay valid and the delivery schema version is unchanged, so an earlier release can still open it. An earlier release that connects a destination again does not update the stored linking user, so after a rollback and a later upgrade the binding can name the previous linker until an owner connects it again on the current release.

Delivery retention is per team: at most 10,000 queue rows across all states and 50,000 attempt rows for each team, so one team's volume cannot pause delivery for another team. Delivered, cancelled and dead letter rows are pruned with their attempt rows 30 days after their last update. When a team reaches either budget, its oldest delivered or cancelled rows are pruned first and its oldest dead letters only after those are gone, so a dead letter can be pruned before an owner retries it. Pending and in-flight rows are never pruned. A team pauses only while its budget is held entirely by undelivered rows. Queue capacity then pauses collection before the first eligible unqueued inbox item, preserving its cursor and the inbox record, and collection resumes as sends finish. Attempt capacity pauses that team's new sends until an owner disconnects or connects the destination again, which cancels the undelivered rows and makes them prunable. An owner retry first discards the retried delivery's earlier attempt records, so it holds no more attempt records than a new delivery, then prunes that team's other delivered, cancelled or dead letter rows until the team has room for all five of its attempts, in the same transaction. Each undelivered row therefore holds at most five attempt records, and 10,000 queue rows can hold at most the 50,000 attempt budget, so a retry cannot leave the team's sends paused behind its own earlier attempts. If the team's other undelivered rows hold that room, the retry is refused with `delivery_capacity` and nothing changes, including the discarded records; the workspace then reports that nothing changed and keeps its controls available. A delivery that an earlier release retried keeps its earlier attempt records until it finishes. Status reports the viewing team's pauses; worker results report whether any team is paused. Pruning removes delivery records only, never inbox items or journal events, so a missing delivery record does not establish that nothing was sent. Pruning audit policy: worker prunes, by age or at a budget, leave no audit entry and no count, because audit entries name the team member who acted and the worker acts for no member, and status counts cover only retained rows. An owner retry records what it pruned in its `telegram.delivery_retried` audit entry: `pruned` counts the team's other deliveries it removed and `dropped_attempts` counts the retried delivery's discarded attempt records. These are row budgets, not a byte limit for the entire workspace database or its WAL.

## Extended investigations and valuations

Historical jobs are private to a team. Viewers can read results; editors and owners can create, cancel and retry jobs. Jobs advance one provider page per tick and share history provider budgets. A job yields to a due watched account only while the history worker's heartbeat is at most 30 seconds old, so a stopped or stalled history worker never holds jobs back. A yield keeps the job `queued` with `last_error` set to `watch_priority`, which the workspace shows as paused while due watched accounts are polled, and makes it eligible again 10 seconds later. After three yields in a row (`intel/investigation_jobs.py:MAX_WATCH_YIELDS`) the job reads its next page without yielding. A saved page clears `last_error` and starts the count again, so however many accounts are watched, watch priority holds a job back for at most three such pauses before each page. A durable provider budget refusal keeps the job in `retry_wait` with `last_error` `provider_budget` until its retry time and does not count as a failed attempt. Other waits, for a provider cooldown, the one read per account per minute, the global page budget, archive capacity or job byte capacity, show `history_capacity` and retry after at least 60 seconds. Each backfill and job read keeps one checkpoint per account and kind, holding its lease and the one read per account per minute. A job read for a new account waits while 20,000 checkpoints are kept; it first deletes every checkpoint whose lease has ended and whose minute has passed, so finished reads never hold job reads shut (`intel/history.py:AccountHistory.claim_job_read`).

Each team holds at most 10 active jobs (queued, running or waiting for retry) and at most 100 retained jobs in all states (`intel/investigation_jobs.py:MAX_ACTIVE_JOBS`, `intel/investigation_jobs.py:MAX_TEAM_JOBS`). Creating a job, or retrying a failed or cancelled one, while the team has 10 active jobs is refused with `job_capacity` and changes nothing; retrying a job that is waiting for retry does not add an active job. When a team already holds 100 jobs, creating one first removes that team's oldest finished jobs, by creation time, until it holds 99. Finished means completed, cancelled or failed. Job request, progress, rows and observations count against a 16 MiB byte share per team (`intel/investigation_jobs.py:MAX_TEAM_JOB_BYTES`) and a 64 MiB bound across all teams (`intel/investigation_jobs.py:MAX_JOB_BYTES`). When a new job, or the next page of a running job, would take its team past the team share, that team's own oldest finished jobs, by creation time, are removed until it fits. When it would take all teams past the 64 MiB bound, the oldest finished jobs of any team are removed, oldest first by the time each last became completed, cancelled or failed, until it fits, so four teams holding full shares cannot lock out a fifth. Every finished job is also removed 30 days after that time (`intel/investigation_jobs.py:RETENTION_MS`), the same period as Telegram delivery retention, oldest first and at most 1,000 per job creation or worker tick (`intel/investigation_jobs.py:MAX_EXPIRED_PER_WRITE`), whether or not its team returns. Cancelling a job that is already cancelled does not restart that period. Queued, running and waiting jobs are never removed. If nothing finished is left to remove, a new job is refused with `job_capacity`. Each of these checks also keeps 10 bytes free for every active job counted against that bound (`intel/investigation_jobs.py:CAPACITY_STOP_BYTES`), the space a job needs to record stop reason `job_capacity`, so ending a job that way never takes usage past its team share or the 64 MiB bound. For the same reason, retrying a failed or cancelled job is refused with `job_capacity` and changes nothing when that room is not left after removing finished jobs. Each time the worker takes a job, before it checks the archive, the page budgets or watch priority and before it reads the provider, the job checks that its team share and the 64 MiB bound have room for the larger of 2,048 bytes (`intel/investigation_jobs.py:MIN_JOB_ROOM`, more than the largest new job takes) and the size of its last page that did not fit, removing finished jobs as above. When there is no room, the job does not read the provider. When a page it read does not fit, the page is not added to that job; the shared archive may already hold that page. Either way the job stays queued with `history_capacity`, retries at least 60 seconds later and does not count the wait as a failed attempt, so a full job store does not fail a job created with the reserved stop space. A job created by the previous release can instead end as failed with `job_capacity` when that space is unavailable, as described below (`intel/investigation_jobs.py:InvestigationJobs.tick`). After three such waits in a row (`intel/investigation_jobs.py:MAX_CAPACITY_WAITS`), the job ends as completed with stop reason `job_capacity`, keeping the pages it already saved; a graph job ended this way keeps its retained transfers but has no graph to download. A job whose final result does not fit ends the same way. A check that finds room, or a saved page, starts the count again. A job ended this way cannot be retried; create a new one. A job created before that 10-byte room was kept, which still finds no such room when it ends even after finished jobs are removed, ends as failed with `job_capacity` instead and keeps its saved pages and its body unchanged; retrying it is refused with `job_capacity` until that room exists. The count only advances when the job is due, which a provider cooldown can postpone, and a running worker takes it. So while the worker runs, active jobs that lack that room end after three waits, whether or not the archive is also full and even when their team never returns, and as finished jobs they can then be removed to make room. Waits for the provider, the page budgets or archive capacity never count toward this limit and never end a job. While the archive, at the limits job pages use, has no room for one more page (`intel/history.py:MAX_ARCHIVE_PAGES`), for 100 more rows (`intel/history.py:MAX_ARCHIVE_ROWS`), the most one page holds, or for 4 MiB more bytes below the 112 MiB that pages and rows may use, the byte budget less its 16 MiB event share (`intel/history.py:MAX_ARCHIVE_BYTES`, `intel/history.py:EVENT_ARCHIVE_BYTES`, `intel/history.py:JOB_PAGE_BYTES`), twice the 2 MiB document limit (`intel/history.py:MAX_DOCUMENT_BYTES`) and so the most one accepted page and its rows take, no job reads the provider, even for a page the archive already holds, and each waits with `history_capacity`. Every job sees the same archive check, so no job takes a page to the job store while others wait on the archive. Any team's finished job can make room under the 64 MiB bound, but only the team's own finished jobs can make room under its share. A team can hold at most its own 16 MiB share, so it cannot use up the bytes other teams need. Removing a job deletes its rows and observations and returns their bytes to the budget in the same transaction; the job then answers 404 like an unknown job. Removal is silent: no audit entry and no job record shows it, either for the team that held the job or for the team whose create or page caused it. When a create causes it, only that create is audited, as `investigation.created`; when expiry or a running job's next page causes it, nothing is audited.

Transfers and transaction jobs retain at most 100 pages and 5,000 rows. Graph jobs support depth up to five, at most 50 queried accounts and 200 retained transfers. These bounds do not establish complete history or account ownership. Progress retains source observations and reports unread pages, failures and limits. A job that reads rows the archive already holds unchanged cites those retained pages with their own source and observation time.

Valid provider Retry-After delta-seconds or HTTP dates are retained as cooldown deadlines. A job retry cannot bypass that deadline; other jobs, backfills and watches using the same account and provider kind share it. Unrelated accounts and provider kinds remain eligible. The history database retains its base schema version 2 with additive cooldown and job page budget tables, so the previous release can read the retained state during a code rollback. The investigation job database also keeps schema version 2: opening it adds `watch_yields`, `capacity_waits` and `capacity_need` columns with default 0, an index on job observations, an index on finished jobs and a per-team byte usage table in place, and rebuilds that table and the total byte count from the retained jobs on every open. Jobs the previous release wrote are therefore counted, expire and can be removed like new ones, existing jobs stay valid and the previous release can still open it.

The entity directory is a curated collection of exact mainnet account associations supported by official publisher excerpts, hashes and retrieval dates. It is separate from verdict labels. An association is not proof of current ownership. Missing source excerpts are withdrawn; changed documents and stale checks remain visible rather than silently refreshing evidence.

Portfolio observations use exact balance strings, contract metadata and contract-keyed prices. Missing, stale or low-confidence prices stay unavailable. A known subtotal is distinct from a complete total. Current indexed token balances may come from different blocks; delegated staking positions, NFTs and DeFi deposits are excluded. Historical reads use actual archival state at the selected block and only the explicitly selected contracts, so the inventory remains incomplete. Retained chart points describe actual observations, grouped by asset scope; they do not reconstruct continuous history or establish investment returns.

The workspace API allows 120 requests per client per minute and accepts JSON mutations up to 32 KiB. Authentication has tighter limits: 10 requests per minute per client, with registration and recovery each capped at five per hour per client. The live API's default is 60 requests per client per minute and eight upstream reads in all, at most four per client including two heavy reads. Each client can have 12 admitted requests, and waits for a turn or slot last at most five seconds from arrival. Provider plans impose their own additional limits. Requests can return unavailable, busy or rate-limited responses; these must remain visible.

## Release update and rollback

Run the live checkout's own `deploy/update.sh <full 40 character commit sha>` from a clean `/opt/siyab`. It fetches the candidate and runs the offline suite and hygiene check in a temporary detached worktree before changing the live checkout. A failed check leaves the live checkout and services unchanged. A passing candidate is checked out, then the script restarts `shieldbot-near-feed.service`, `shieldbot-near-api.service`, `siyab-api.service`, `siyab-delivery.service`, `siyab-history.service`, `siyab-investigation.service` and `siyab-monitor.service`. The two legacy units run from `/opt/shieldbot-near` (`deploy/shieldbot-near-api.service:10`, `deploy/shieldbot-near-feed.service:10`), a checkout this script neither moves nor restores.

If that restart fails, the script checks out the previous SHA and retries the same unit list. It exits nonzero even when the recovery restart succeeds. If that restart also fails, it reports the recovery failure on stderr; inspect the service status and logs before treating the release as running. This restores code only, not external state. Keep the state backups below separate from releases (`deploy/update.sh`).

## Backup and recovery operations

For a transactionally consistent workspace-only backup, choose a new external destination:

```sh
python -m intel workspace-backup --state-dir /var/lib/shieldbot-near/siyab --out /var/backups/siyab/workspace-YYYYMMDD-HHMMSS.sqlite3
```

Replace the timestamp before running. The destination must be outside the repository and must not already exist. The command reserves the path exclusively and uses SQLite's backup API. It includes private account/team state, sessions, recovery hashes, notes and Telegram delivery state; restrict access accordingly. It does not include other state databases, external feed evidence or browser-only data.

For a full state snapshot, stop the API and all four workers, then copy the entire external state directory, including any WAL/SHM sidecars, before restarting. Retain the external feed evidence separately if replay of retained-feed files is required. Keep release code and state backups distinct.

To restore, stop all five services and restore into a separate external directory. Check each restored SQLite database with `PRAGMA integrity_check`, restore the service user's ownership and private permissions, and point all five service commands to the same restored directory before restarting. Retain the previous state directory for rollback. Restoring workspace state also restores session and recovery hashes from that snapshot; do not assume a code rollback revokes sessions.

Team JSON exports are portable case/watch backups, not full account, inbox or audit backups. Browser-only JSON exports remain separate and are the user's responsibility. Neither the shared platform nor these operational commands change financial signing, Gate policy, testnet contract configuration or mainnet write authorization.
