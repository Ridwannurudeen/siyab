# Reports contract

Reports source version is `0.1.3`; testnet runs deployed Reports version `0.1.2`. The contract fixes the non-refundable deposit at exactly `REPORT_DEPOSIT`, 30000000000000000000000 yoctoNEAR (0.03 NEAR; `contracts/reports/src/lib.rs:9`, `:853-858`). It rejects moderation by either the report submitter or subject (`:431-432`) and always refuses dispute resolution by the report subject (`:670`). With more than one moderator, it rejects resolution by the report submitter or dispute submitter (`:692-696`) and checks the original accepting moderator stored under prefix `ab` (`:515-516`, `:675-716`); if the `ab` entry is absent and `upheld_disputes` is 0, it falls back to `report.moderator` and writes that accepter to `ab` before changing `report.moderator`. With more than one moderator, it fails closed if the `ab` entry is absent and `upheld_disputes` is above 0. Reports version 0.1.2 has no lifetime cap on disputes.

`submit_report` and `dispute` keep their attached deposits in the contract account in every state. `withdraw` returns nothing, and no method refunds a report or dispute deposit. Report and dispute rows are permanent: state changes update them in place, and the contract has no row deletion or refund method. `Report` stores accepted-chain links (`accepted_prev`, `accepted_next`), deny-chain links (`deny_prev`, `deny_next`), and `upheld_disputes`, a statistic of disputes resolved against the disputer, saturating at 255. In source version 0.1.3, `report_and_dispute_storage_measurement_is_pinned` measures 2,046 bytes for one maximum-size report through acceptance and 734 bytes for one maximum-size dispute and pins both exactly. With `measured` set to the larger byte count, the test asserts `measured * byte_cost * 120 / 100 <= REPORT_DEPOSIT <= measured * byte_cost * 2` and pins `REPORT_DEPOSIT` at 30000000000000000000000 yoctoNEAR (0.03 NEAR). This fixed price was chosen to cover at least 1.2 times the measured worst-case storage; `report_deposit()` exposes it, so it does not move with each storage change. `new` and `set_moderators` refuse a moderator list that names the same account twice (`REFUSED:duplicate_moderator`), so the single moderator exception counts distinct accounts. The sandbox test proves the report and dispute deposits remain in the contract account after overturn.

`subject` means **the account agents should not pay; never a victim**.

The canonical report body behind `body_sha256` has exactly the fields `evidence_sha256`, `evidence_url`, `kind`, `outcome`, `subject`, and `submitter`. Serialize them as UTF-8 compact JSON with keys in that sorted order, no spaces, and no null fields, then hash those bytes with SHA-256. `fixtures/records/body-vector.json` is the shared Rust and Python test vector.

Kinds, outcomes, and states serialize as the lowercase values in `intel/record_enums.json`. `rust_enum_values_match_the_canonical_json` compares the contract enums to that file. `deny_follows_kind_alone_for_every_outcome_when_accepted_and_contested` checks all 24 kind/outcome pairs in both accepted and contested states.

The only report state changes are pending to accepted or rejected by a moderator, pending to withdrawn by the submitter, accepted to contested by a dispute, and contested to accepted or overturned by a moderator. `all_disallowed_report_state_transitions_are_refused` exercises every other transition from every non-pending state; the method tests above prove each allowed transition. Rows remain stored through every transition.

A report can still lack an `ab` entry after an upheld dispute only when it already had at least one upheld dispute under 0.1.1 before the 7 Nov redeploy. Under 0.1.2, when `ab` is absent and no dispute has been upheld, the fallback writes `report.moderator` to `ab` before changing that field. In a legacy report where the accepter is already unknown, while multiple moderators are configured, every resolution is refused with `REFUSED:same_moderator`. The testnet Reports contract holds zero reports, so no such report exists there. If one ever existed, the owner could make it resolvable by calling `set_moderators` with a one-moderator list; the method is owner-only and requires exactly 1 yoctoNEAR. No migration method exists; a future migration could also restore the missing accepting-moderator entry.

Source version 0.1.3 emits the `shieldbot-near` NEP-297 envelope version `1.1.0`; testnet's deployed version 0.1.2 emits `1.0.0`. At threshold 1, the payloads of the existing events remain unchanged, while every envelope carries the new version. The existing events are `moderators_updated`, `report_submitted`, `report_moderated`, `report_withdrawn`, `report_disputed`, and `dispute_resolved`. Source 0.1.3 also emits `approvals_required_updated` and `report_vote`. The moderator update contains the new moderator list. The report and dispute events include the report id, subject, state, and report body hash; `report_disputed` and `dispute_resolved` also include the dispute id, and `report_moderated` and `dispute_resolved` also include the moderator and the reason hash. `owner_can_set_moderators` proves the moderator update event, and `emits_all_five_nep_297_events_with_report_identity` checks the report and dispute event payloads.
