# NEP-413 and encrypted personal workspaces

22 Nov 2026. Branch `feat/nep413-workspace`, now at `39f9446ff` after the existing main merge. The original lane was based on `0e113268c`; the dated validation rounds below retain their historical results.

## What this lane adds

The workspace has three explicit destinations. Browser storage remains the default. A NEAR wallet can sign in to a personal encrypted copy, which moves only when its owner chooses Save encrypted copy or Merge into this browser. Existing shared teams retain their separate password sign-in and readable server data for collaboration and workers.

Signing in and unlocking never upload local investigations. No transaction, access key creation, payment or model call is part of this feature. Its only chain request is a public mainnet access key read during sign-in.

## Sign-in

`intel/near_auth.py` reuses `gate.ed25519`, `gate.base58`, `gate.canon` and `gate.rpc`. `gate/outlayer.py` was inspected and has no NEP-413 serializer. The new serializer implements only the protocol encoding. The existing Ed25519 verifier performs signature verification, with additional prime subgroup and identity-point rejection using its existing point operations.

The server issues a random 32-byte nonce and challenge identifier, binds them to an HttpOnly browser cookie, the claimed mainnet account and the configured Siyab origin, and records an expiry five minutes later. The sign-in message includes the account, origin, identifier and issue and expiry times. The recipient is the full configured origin. The signed callback is that origin plus `/workspace.html`.

Before opening the wallet, the browser independently reconstructs the exact sign-in message from those fields and the fixed five-minute lifetime. A challenge cannot request the separate unlock message and then send that signature to the server as authentication. The regression test substitutes the actual unlock payload into an otherwise valid challenge and verifies that the wallet is never called. Changing the sign-in header, identity, times, callback or challenge identifier also refuses before signing.

The payload contains little endian u32 `2147484061`, a Borsh message string, the raw 32-byte nonce, a Borsh recipient string and the optional callback string with its one-byte presence tag. Strings use UTF-8 byte lengths. The verifier checks Ed25519 over SHA-256 of these bytes, as required by NEP-413. State is a separate response binding, not a serialized payload field. Sources: [NEP-413](https://github.com/near/NEPs/blob/master/neps/nep-0413.md), [Borsh](https://borsh.io/) and the [official SDK schema](https://github.com/near/near-api-js/blob/master/src/nep413/schema.ts).

The challenge is deleted in an immediate SQLite transaction before verification. A concurrent verification, retry after a failed signature, browser mismatch, wrong account, nonce, recipient, callback or state, and an expired challenge all fail. The account and public key come from a current `query` request with `request_type: view_access_key` and `finality: final`. Only the exact permission `FullAccess` passes. Missing, deleted, function-call-only, unsupported gas keys and malformed or unavailable RPC results refuse sign-in. Fixture replay is refused. Expiry is checked again after the RPC read. The request and permission shapes are verified against the [official RPC reference](https://docs.near.org/api/rpc/contracts#view-access-key).

Successful verification creates a separate one-hour wallet session, with a CSRF token, strict origin binding, HttpOnly, SameSite=Strict and Secure on HTTPS. The challenge step uses its own five-minute cookie, `__Host-siyab-near-challenge`, separate from `__Host-siyab-near-session`. Local HTTP uses the corresponding `siyab-local-near-` names. A session read in another tab cannot clear the challenge cookie. Reauthentication rotates an existing session token. A password session neither opens nor modifies the personal vault. Wallet sign-in neither joins a team nor imports its data. Sessions are stored by token hash. A deleted signing key fails the next sign-in; an already issued cookie remains valid until logout or its one-hour expiry. It is not rechecked on every vault request.

Challenges and verification each have a five-per-minute address limit, in addition to existing request limits. Open challenges also have a persisted cap of eight per IPv4 /32 or IPv6 /48, enforced in the same immediate transaction as the global 4096 cap. Eight permits several simultaneous wallet tabs while limiting one network to less than 0.2 percent of the global open-challenge slots. Users behind carrier-grade NAT share the eight slots, so a busy shared public IPv4 address can delay legitimate sign-ins until another challenge is consumed or expires. IPv4-mapped IPv6 addresses use the IPv4 bucket. Expired challenges stop counting. An upgrade from the previous unbucketed schema expires outstanding challenges once; users start sign-in again, while sessions and vaults remain intact. Multiple independent address buckets can still exhaust the global cap. Address normalization follows [Python ipaddress](https://docs.python.org/3.12/library/ipaddress.html).

Access key verification uses the separate `near_auth` provider caller class, with 500 calls per UTC day, 100 per hour and 30 per minute for both keyed and keyless FastNEAR RPC. It does not increment anonymous public lookup counters. Existing pooled keyed and provider-wide keyless ceilings still apply. These durable limits require the existing provider budget database, which the stateful serve entry point configures.

Before each access key RPC lookup, atomic persisted counters permit at most 20 lookups per UTC day, eight per UTC hour and three per UTC minute for the challenge's recorded IPv4 /32 or IPv6 /48 bucket. This applies across accounts, keys, browser cookies, workers and restarts. Twenty allows twenty fresh key checks per shared address each day while requiring at least 25 buckets to consume the shared 500-call daily allowance. Three IPv4 addresses can consume at most 60 calls per day and nine per UTC minute. Four IPv6 /48 buckets can consume at most 80 per day and 12 per UTC minute. Four buckets can produce at most 24 calls across a minute boundary, also below 30. Reaching 30 within one UTC minute requires at least ten buckets. Each counter table holds at most 4096 active rows without evicting active counters; a full table refuses new buckets. All three allowances and both capacity checks run before any counter is incremented in the same immediate SQLite transaction. Failed RPC requests still consume their reserved lookup. Users behind carrier-grade NAT share these allowances, so a busy public IPv4 address can delay legitimate sign-ins. Distributed traffic with at least 25 daily buckets or ten minute buckets can still spend the corresponding shared allowance, and unrelated provider traffic can also reduce availability.

On upgrade, the new daily table is seeded from retained hourly counters, with the current hour conservatively counted against the current minute. The old limiter already deleted earlier-hour rows, so their calls cannot be reconstructed. The complete daily bound starts with the next UTC day; the activation day preserves known usage and admits at most 20 further checks per bucket. SQLite's immediate transaction behavior is documented in the [transaction reference](https://www.sqlite.org/lang_transaction.html).

A confirmed `UNKNOWN_ACCESS_KEY`, the exact legacy missing-key error described in the 22 Nov update below, or a schema-validated access key without ordinary `FullAccess` is cached for 60 seconds per exact account and public key. A repeat still needs a valid fresh single-use challenge and signature, but consumes neither a bucket lookup nor a provider call. This negative cache is persisted and bounded to 4096 entries. A key added or upgraded during that minute can remain refused until the entry expires. Successful keys are always checked afresh. Transient failures, malformed responses and structured `UNKNOWN_ACCOUNT` are not cached. Error variants and context fields were checked against the [nearcore query error source](https://github.com/near/nearcore/blob/master/chain/jsonrpc-primitives/src/types/query.rs); access key permission forms are in the [RPC reference](https://docs.near.org/api/rpc/contracts#view-access-key). The cache duration and numerical caps are Siyab policy choices.

## Encryption format and recovery

`intel/ui/workspace-vault.js` uses browser WebCrypto. The browser asks the wallet to sign a fixed, domain-separated unlock message. This is distinct from the sign-in challenge and includes the origin, mainnet account and exact Ed25519 public key. Its fixed 32-byte nonce is SHA-256 of a JSON array containing a separate nonce domain and the same identity. The callback is always `origin + /workspace.html`.

The browser verifies the exact NEP-413 digest and signature locally, requests the same message a second time and requires the signatures to match byte for byte on every unlock. HKDF with SHA-256 derives a nonextractable AES-256-GCM key from this signature, with separate salt and key domains. Neither unlock signature nor derived key is sent to the API or written to localStorage or sessionStorage. Signature byte buffers are cleared after derivation; JavaScript strings and browser-managed copies cannot be guaranteed erased.

Each save creates a random 12-byte IV. The encrypted JSON uses a 128-bit GCM authentication tag and a 512 KiB UTF-8 plaintext limit. The versioned envelope has exactly these fields:

```json
{
  "version": 1,
  "algorithm": "AES-256-GCM",
  "derivation": "NEP413-HKDF-SHA256-v1",
  "origin": "https://siyab.xyz",
  "account_id": "account.near",
  "public_key": "ed25519:<base58 public key>",
  "vault_id": "workspace:<revision>",
  "iv": "<standard padded base64 of 12 bytes>",
  "ciphertext": "<standard padded base64 of ciphertext and authentication tag>"
}
```

Authenticated additional data covers the protocol domain, format version, algorithm, derivation, origin, account, key and revision-bound vault identifier. The API accepts only that field set and canonical base64 lengths. The ciphertext maximum is 524304 decoded bytes. The dedicated vault POST allows a 1 MiB body only after the NEAR session cookie resolves through an indexed database read to a current session for this exact origin. Otherwise, the HTTP handler refuses a declared body over 32 KiB before reading any body bytes. Fake well-formed tokens, expired or revoked sessions, other-origin sessions, challenge cookies, malformed or duplicate cookies and unavailable session storage do not grant the larger limit. Session authentication and CSRF are still required before storage. Other workspace requests retain 32 KiB. The original request framing and body deadline checks remain. Crypto parameters and nonextractable derivation were checked against [WebCrypto](https://www.w3.org/TR/webcrypto/) and are tested against independent Node crypto HKDF and GCM implementations.

Opening another device requires the same origin, same account, same Full Access signing key and byte-identical wallet signatures. It requires only the wallet holding that key, with no server password or extra recovery secret. A new key for the same account derives a different encryption key. A hardware wallet, mobile wallet, MPC signer, imported account with a different key or a signing implementation that randomizes signatures is not promised recovery. An existing encrypted copy must decrypt successfully before saves are enabled. The server also rejects overwriting an existing vault with a different signing key and uses optimistic revisions to refuse stale device writes.

Keep a local JSON export before rotating or removing the signing key. Account recovery alone does not recover the old encrypted copy. There is no silent reset or automatic key replacement. Browser exports and data merged back into browser storage are readable on that device. Lock and sign-out drop the in-memory encryption handle; they do not erase existing browser saves. Leaving the page locks the handle, including return through the browser page cache. JavaScript cannot promise immediate physical erasure of browser cryptographic memory.

`POST /workspace-api/near/vault/reset` is an explicit destructive recovery path. It requires the exact configured Origin, the wallet session CSRF token, a NEAR session created less than five minutes ago and exactly `{"confirmation":"DELETE account.near"}` for the signed-in account. It removes only that account's ciphertext for that origin and leaves a tombstone with an incremented revision. The existing non-null envelope column stores JSON `null`, returned as `vault: null`. Repeated resets also increment the revision. The next save uses the tombstone revision and writes the next revision, so a stale save from before reset cannot resurrect the old copy. A tombstone permits the current signing key to save a new copy. The previous ciphertext is lost; it cannot recover old notes without the original key. The panel warns before the typed confirmation, remains available when a changed key blocks loading, and preserves browser saves and shared teams. A successful reset locks the encryption handle and lets the current key start a new vault. A 409 locks writes but keeps the session and reset controls. Only a 401 clears the client session in response to an HTTP error.

The browser remembers the highest validated revision it has read, reset or successfully saved for each origin, account and public key. `readVault` refuses an older revision, including a missing row after a previously seen save. A confirmed local reset also records its exact revision under a separate key for that same identity. A matching tombstone shows that the vault was reset on this device, including after a reload or new sign-in. A later tombstone without a matching local reset shows reset elsewhere. The client preserves browser data and permits unlocking to save a new copy. A tombstone below the high-water mark still fails as rollback. A second device with separate storage can load the reset and its replacement without resetting again. These localStorage records contain only identity and revision metadata. Storage access is guarded, and in-memory records keep the page usable when browser policy or quota refuses persistence. After a reload without working storage, the reset message makes no device attribution. The panel states that the fallback lasts only until the page closes. Clearing storage, changing profiles or changing the signing key loses the local reset attribution; it is browser evidence, not a cryptographic device identity. Reset never lowers the retained revision, even when storage writes fail. The storage exception behavior follows the [HTML storage specification](https://html.spec.whatwg.org/multipage/webstorage.html#the-localstorage-attribute).

## Supported wallet boundary

ETH-implicit accounts, formatted as `0x` followed by 40 lowercase hexadecimal characters, cannot sign in. This path requires an ordinary Full Access Ed25519 access key. The server and client refuse those accounts explicitly. See the [NEAR account specification](https://github.com/near/nearcore/blob/master/docs/DataStructures/Account.md).

The shipped adapter accepts Sender through `window.near.isSender` and OKX Wallet through `window.near.isOkxWallet`, with a callable `window.near.signMessage`. Sender returns a wrapped `response`; its existing error handling remains. OKX returns the signed object directly. Both paths retain response shape, account and state checks and forward the exact message, recipient, typed-array nonce and callback. Before an OKX signature, an empty `getAccountId()` triggers only `connect({})`, without `contractId` or `methodNames`. Sender never connects through this adapter. Neither path calls `requestSignIn`, adds a key or submits a transaction. Sources: [Sender adapter](https://github.com/near/wallet-selector/blob/main/packages/sender/src/lib/sender.ts), [injected interface](https://github.com/near/wallet-selector/blob/main/packages/sender/src/lib/injected-sender.ts) and [OKX NEAR provider](https://web3.okx.com/onchainos/dev-docs/wallet/dapp-connect/chains/near/provider). The installed OKX connection and callback checks are recorded below.

Sender now also documents `window.sender.near`. That path is not silently assumed equivalent and is not enabled here. An installed Sender version must expose the selected interface, accept the 32-byte typed-array nonce and preserve the exact callback payload. If it cannot, sign-in or local signature verification refuses. The actual wallet signer implementation and its cross-device determinism were not independently attested. Automated tests use real cryptography with a local test signer; they are not a claim of a live wallet approval. The owner's live Sender check below is a merge gate. Current injection documentation: [Sender account access](https://docs.senderwallet.io/guide/access-accounts/access-accounts-in-near).

RFC 8032 specifies deterministic Ed25519 signing, but this does not establish that every wallet uses that signing procedure or the same key. WebCrypto also permits randomized Ed25519 signature generation. Two identical signatures are a runtime compatibility gate, not a proof about all future signatures. Sources: [RFC 8032 signing](https://www.rfc-editor.org/rfc/rfc8032#section-5.1.6) and [WebCrypto Ed25519](https://www.w3.org/TR/webcrypto/#ed25519-operations).

MyNearWallet popup support was rejected after reading its actual callback handling: that path omits the callback from the signed payload when an opener exists. No fallback drops the signed callback to make such a path pass. Source: [MyNearWallet signing wrapper](https://github.com/mynearwallet/my-near-wallet/blob/master/packages/frontend/src/routes/SignMessageWrapper.js). Meteor SDK forwards signing inputs, but its actual signer and cross-device behavior were not verified, so it is not shipped as an additional adapter.

## Privacy and remaining visibility

With the delivered client behaving as implemented, the personal vault API receives encrypted JSON and stores no case title, note, investigation URL, watchlist member or notification text. A database copy, workspace backup or passive operator inspection cannot decrypt it from the authentication signature. That signature signs a different message and nonce from the unlock signature.

The server still sees the NEAR account and signing public key, origin, IP address, session and challenge activity, ciphertext sizes, revisions, record presence, and read and write timing. Its RPC provider sees the account and public key being checked. Public account lookups and feed traffic remain visible. This design does not hide traffic patterns or prevent server deletion. The browser refuses a server rollback below a revision it has already retained for that exact identity. A new device, cleared browser storage or lost persistence cannot detect an older valid snapshot without an independent retained revision. Revision AAD prevents envelope substitution; local revision memory adds only this bounded rollback check.

This is protection against readable server storage, not a claim that a server can never learn plaintext under any circumstances. A server delivering modified JavaScript, XSS, a malicious extension, a compromised browser or a wallet that leaks unlock signatures can defeat it while the workspace is unlocked. Recipient text alone does not prove the calling web origin. Another origin could request the same fixed unlock payload unless the wallet enforces origin binding or the user refuses it. Only approve the unlock message from the exact Siyab origin. Sender's public adapter does not establish that the wallet enforces this boundary. NEP-413 itself explains recipient inspection as a mitigation rather than an automatic browser guarantee.

## Features that require server plaintext

Personal encrypted watchlists match the public feed in the existing open browser. They are not enrolled in background account polling, retained team inboxes, queued historical investigations, shared cases, server Ask requests or Telegram delivery. Those features continue to work in explicit shared teams with their existing readable records, role checks, worker bounds and separate password sign-in. Server workers cannot match encrypted account identifiers without obtaining those identifiers. No private data is copied into a team or a public account archive by this feature.

This lane does not encrypt or delete previously saved team cases and watches. It makes their readable destination visible next to the encrypted destination. A team encryption protocol with member key distribution and private server-side watch matching is outside the implemented boundary. Shared imports still require their existing explicit confirmation.
