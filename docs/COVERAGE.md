# NEAR ecosystem coverage

Siyab is security intelligence for the NEAR ecosystem. This table describes code available on this branch, not adoption by any wallet or protocol, current external service availability, or coverage of every ecosystem risk. Registry membership and reported metadata do not establish ownership.

Account and token checks are off by default; `SIYAB_CHECKS=1` enables their live routes (`intel/live.py:128-129`). Proposed transaction checks are opt-in with the same flag in MCP (`mcp/server.py:280-282`, `mcp/server.py:308-310`) and, with `SIYAB_TELEGRAM_CHECKS=1` too, in private Telegram chats for a pasted mainnet transaction hash whose actions are read from FastNEAR (`gate/txfetch.py:fetch_transaction`); the Telegram path answers account and token checks behind both flags as well and is off by default (`intel/delivery_checks.py:TelegramChecks.answer`). They inspect the actions using local labels and incident records (`gate/txcheck.py:140-223`). These checks return unsigned advice. An unknown observation remains unknown; without a deciding signal it produces ASK, never ALLOW. Only the testnet Gate enforces payment policy on a signed ALLOW bound to the exact transfer (`contracts/gate/src/lib.rs:150-210`).

| Group | What Siyab covers today | What it does not cover |
|---|---|---|
| Wallets | Account and access-key checks; proposed transaction warnings for full access key additions, account deletion, code deployment, receiver labels and lookalikes (`gate/account_check.py:148-262`, `gate/scan.py:26-37`, `gate/txcheck.py:147-203`). A reference Wallet Selector guard checks `signAndSendTransaction`, `signAndSendTransactions` and `signIn` against hosted checks (`integrations/wallet-selector/adapter.mjs:344-390`). | Checks do not intercept wallet signing unless the host routes the operation through its guard. Reference adapters are not adopted wallet integrations. The Wallet Selector maintainers have not reviewed, adopted or acknowledged this adapter (`integrations/wallet-selector/README.md:5`). Unmodelled calls and unassessed code remain unknown; there is no transaction simulation. In rules versions 1 and 3, `code_without_metadata` reads an empty local code hash as no contract code even when the account reports a global contract; only version 2 drops that check for a reported global contract (`gate/rules.py:976-982,1082-1087`). The three seeded Rhea accounts' old "account exists with no contract code" assertions are superseded by observations naming their global contract hash (`intel/labels.jsonl:394-396,3284-3286`; `gate/rules.py:184-185`). |
| DEXs and DeFi | Standalone token catalog, metadata, symbol and name comparisons, full access key control observations and incident code matching (`gate/token_check.py:227-312`). | No contract audit, collateral valuation or complete token behavior analysis. A catalog entry is not approval to list a token. |
| NEAR Intents and 1Click users | Unsigned quote and supported destination-recipient preflight with evidence and request binding (`gate/intents.py:1-41`). A local settlement command for wNEAR to an EVM address judges the recipient, checks a non-dry quote and its manager signature, funds one deposit of at most 0.25 wNEAR only with `--deposit`, and reconciles the destination receipt (`gate/oneclick.py:28,179-189,348-448,759-972`). One owner-funded 0.1 wNEAR run settled on 22 Nov 2026 (`fixtures/runs/oneclick-mainnet-20261122.txt:5-22`). | No Gate or contract enforcement of settlement: recipient judgement and reconciliation are unsigned local results (`docs/lanes/oneclick.md:11`). Only the wNEAR origin and EVM destinations are implemented (`gate/oneclick.py:26-28,759-777`). The `intents` preflight and MCP tool pass no signature verifier and stay dry, and a deposit address supplied to them cannot produce ALLOW (`gate/intents.py:497-501,661-743,924-953`). No SHIELD integration. |
| DAOs and treasuries | Recorded factory membership, account and key checks, and checks of supplied proposed transactions (`intel/registries.py:65-72`, `gate/account_check.py:148-262`, `gate/txcheck.py:140-223`). Optional group alerts require an owner-started link, a verified group administrator or creator and owner confirmation (`docs/WORKSPACES.md`). | Group delivery is off by default in the code behind `SIYAB_TELEGRAM_GROUPS`; the hosted deployment enables it after an operator live check that this repository does not record. Everyone in the connected group receives the team's alerts; administrator status is checked only during linking. No DAO proposal reader or proposal-specific interpretation of upgrades, policy changes or role changes. Factory membership is not a judgement on a proposal. |
| Validators and staking pools | Recorded validator registry membership, current stake and epoch observations, and account key checks (`intel/registries.py:74-81`, `intel/identity.py:80-103`, `gate/scan.py:26-37`). | No pool owner or fee-change tracking, kickout history or validator risk rating. Membership is an observation, not an endorsement. |
| Bridges, Chain Signatures and Aurora | Recorded bridge factory labels, issuer blacklist facts and token checks (`intel/registries.py:92-99`, `intel/issuers.py:1-31`, `gate/token_check.py:227-312`). Offline derivation of Chain Signatures child keys and Ethereum, Bitcoin and Solana addresses (`gate/chainsig/__init__.py:102-129`; `gate/chainsig/__main__.py:44-58`). | No bridge, Chain Signatures or Aurora system audit. A derived address is not a verdict, and no MPC signature or target-chain transaction is checked (`docs/lanes/chainsig.md:23-31`). Token answers do not provide a general native, bridged or unlisted classification. |
| Token issuers, launchpads and meme platforms | Token metadata compared with the recorded issuer and catalog corpus, plus catalog, contract-control and incident-code checks (`gate/token_check.py:71-80`, `gate/token_check.py:227-312`). | No universal brand registry, launchpad monitoring or new-token contract audit. Unknown metadata and full access control remain unknown. |
| Retail users | Browser account investigations, payment checks, key scans and Intents destination checks (`intel/render.py:512-551`, `intel/render.py:1892-1920`). NEAR wallet sign-in through Sender or OKX Wallet to a personal copy encrypted in the browser (`intel/ui/near-workspace.js:68-83`; `intel/private_workspace.py:73-155`; `intel/ui/workspace-vault.js:89-119`). | No automatic wallet protection. Proposed transaction checks do not have a browser form. Missing reads and bounded history do not establish a favorable result or complete activity. |
| Exchanges and compliance teams | Sourced labels and unsigned checks can inform an individual investigation (`gate/account_check.py:148-262`). | No screening-at-volume product, compliance determination or service-level agreement. |
| NEAR Foundation, Near One and security responders | Sourced incident records, bounded fund-flow traces, relationship edges with provenance and a finalized-block feed (`intel/trace.py:1-35`, `intel/cluster.py:1-28`, `intel/feed.py:1-19`). | No complete tracing, guaranteed incident response or coverage of every incident. A relationship edge does not establish common ownership. |
| AI agents | Payment verdicts and a testnet Gate that requires a signed ALLOW bound to the exact transfer, with allowlists, denylists, caps, expiry and replay refusal (`contracts/gate/src/lib.rs:150-258`). A reference LangChain tool and send guard (`integrations/langchain/adapter.py:188-213`). | No Gate is in service on mainnet; `siyabgate.near` is paused with its agent key revoked. Payments outside the Gate are not enforced. After the deadline, on 15 Nov 2026, a one-off `siyabgate.near` Gate run refused a labelled collector submission with `REFUSED:no_verdict`, spending nothing, and paid an allowlisted payee 0.01 NEAR under a signed ALLOW; the Gate was then paused and the agent revoked. It is not in `hackathon-submission` (`fixtures/runs/gate-mainnet-20261115.txt:16-38`; `tests/test_mainnet_run.py`). The Gate trusts its configured signing key; unsigned check advice never authorises payment. On 22 Nov 2026 the same account sent a 0.1 wNEAR 1Click deposit with `python -m gate intents-settle --deposit`, signed by the account FullAccess key; the paused Gate contract neither checked nor enforced that transfer (`fixtures/runs/oneclick-mainnet-20261122.txt:5-22`). |

The NEAR Intents destination preflight is a bounded part of the NEAR payment path, not a claim of general coverage on other chains. Recorded incidents do not establish incident counts for account-key phishing, storage-deposit tricks, upgrade abuse or DAO proposal attacks.
