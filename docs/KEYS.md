# Keys and roles

This file lists every key role Siyab uses, who holds each key and how each is changed. It holds no key material, and it names where a key lives only by location class. Accounts are the testnet accounts of `docs/TESTNET.md`; no mainnet contract is deployed (README Limits). The variables are those of `scripts/README.md` and `env.example`.

NEAR separates the key from the account: an account can hold several access keys, and `near account add-key` and `near account delete-keys` (`docs/SPIKES.md:127-128`) replace a key while the account, and every contract field that names it, stay the same. "Rotation" below names both kinds where both exist: the account level key change, and the contract method that moves a role to another account.

## Rules

1. One key per role. Today the testnet owner account `kestrelridge-owner.testnet` is both the Gate owner and the registry owner (`scripts/setup_testnet.sh:117-121`), the deployed reports contract also names it as owner (`scripts/deploy_reports.sh:29-33`, `res/BUILD-reports.md`), and the Gate account now holds the owner key with FullAccess and the agent function call key. The old deploy key was deleted on 9 Nov; this does not separate the owner roles or remove the owner's ability to replace Gate code (`fixtures/runs/gate-022-deploy-20261109.txt`). This is the current state, not the rule met. Before any mainnet deploy each owner role gets its own account and key.
2. The verifier key is never on the hosted box. The hosted services read `/etc/shieldbot-near/env`; the Siyab API, history, investigation and delivery units also load optional `/etc/shieldbot-near/siyab-provider.conf`, and API and delivery load optional `/etc/shieldbot-near/siyab-delivery.conf` (`deploy/siyab-api.service:11-13`; `deploy/siyab-history.service:11-12`; `deploy/siyab-investigation.service:11-12`; `deploy/siyab-delivery.service:11-13`). None of these files may set `VERIFIER_KEY_FILE`, `AGENT_KEY_FILE`, `NEAR_KEYS_DIR` or `GATE_LIVE_SIGNING`, and no NEAR key file goes to the box. Their deployed contents are not recorded in the repository. The API and the feed sign nothing (README Trust model).
3. The recorder key moves off the build machine before any mainnet registry is deployed. This is a requirement, not done.
4. No key material in the repository, in any document or in any script output. The scripts take key files by path only and print no key (`scripts/README.md`); `scripts/check_hygiene.py` rejects private key forms.
5. Every testnet script refuses any network but testnet (`scripts/lib.sh:104-110`).

## If a key is lost or exposed

Act in the order given. Each item names the contract method that recovers; `docs/RUNBOOK.md` gives the commands and the read backs.

- Agent function call key, exposed: run the kill switch (`scripts/kill_switch.sh <agent_pub>`): `set_paused` (`policy.rs:193-196`), `revoke_agent` (`policy.rs:93-103`), `withdraw` of the token balance to the cold account (`policy.rs:231-244`). Register a new key, never the revoked one (`scripts/README.md`). The exposed key can only call `request_transfer`, and every transfer still needs a signed ALLOW within the caps, so the most it can move before the revoke is what the caps allow on verdicts it obtains. Lost: `revoke_agent`, then `register_agent` with a new key and `set_allowlist` again.
- Verifier key, exposed: pause the Gate (`scripts/set_paused.sh true`, `policy.rs:193-196`), run `scripts/rotate_verifier.sh <new_verifier_public_key>` (`set_verifier_keys`, `policy.rs:163-181`), point `VERIFIER_KEY_FILE` at the new key, and stay paused until the previous key's `valid_until_ms` from view `get_verifier_keys` has passed, then resume with `scripts/set_paused.sh false`. The script keeps the exposed key as `previous` for one `MAX_TTL_MS` and no script sets it to null, so during that time a verdict the exposed key signs with `key_id` `prev` still verifies (`verdict.rs:75-86`); the pause refuses every transfer before the verdict is checked (`contracts/gate/src/lib.rs:154-160`). A signature from the exposed key still needs the agent key to be submitted, and stays bounded by the caps and the verdict lifetime (`contracts/gate/src/lib.rs:194-210,212-237`; `contracts/gate/src/verdict.rs:66-73`; `docs/TESTNET.md:52`). The commands are in `docs/RUNBOOK.md`, When the verifier key may be exposed. Lost: `scripts/rotate_verifier.sh` with a new key; until then no ALLOW is signed and every transfer reads `REFUSED:no_verdict`.
- Recorder key, exposed: replace the recorder account's key at the account level, or have the registry owner call `set_recorder` (`registry/src/lib.rs:192-205`) to a new account with `scripts/rotate_recorder.sh`. Records already written stay; a wrong record is superseded by a newer record for the same subject, because `latest` returns the newest (`docs/REGISTRY.md`). Lost: the same two paths.
- Reports moderator, exposed or lost: the reports owner calls `set_moderators` (`reports/src/lib.rs:302-320`) with a list that leaves it out. A moderation it already made stays on chain; a wrong acceptance is corrected through `dispute` (`reports/src/lib.rs:598-660`, `scripts/dispute.sh`) and `resolve_dispute` with `overturn` true (`:662-764`, `scripts/dispute.sh --resolve`).
- Owner and Gate account key, exposed or lost: since 9 Nov the same owner key controls owner methods and is the Gate account's only FullAccess key; no second full access key is recorded (`fixtures/runs/gate-022-deploy-20261109.txt:43-58`). Exposure permits uncapped owner withdrawals up to the Gate balance and verifier replacement (`contracts/gate/src/policy.rs:163-181,231-244`), plus replacement of Gate code, account-level fund movement and access-key changes. Contract pause and caps cannot contain FullAccess authority. While the operator still has the key, recovery requires account-level replacement on both the owner and Gate accounts, verification of the replacement permissions, deletion of the exposed key, and updating the external Gate signing alias. An attacker holding the key can race those steps; if control cannot be retained, move any recoverable funds to a new deployment. If the sole key is lost, no recorded second key can recover owner methods or Gate redeployment; the restricted agent key cannot replace it. No contract method changes `owner_id`.
- Registry, token or reports deploy signer, exposed or lost: account level key change. Whoever holds an exposed key can replace the code on that account, so check the account's `code_hash` against the build record (`docs/RUNBOOK.md`, Deploy, read backs) before trusting a read from it again.
