# Threat model

This model covers the NEAR agent payment path, the MCP and HTTP verdict interfaces, the Gate, registry recording, reports, read-only Intel API, and the OutLayer approver adapter. (gate/agent.py:286-361; mcp/server.py:152-185,188-222,225-236,244-279,282-312; gate/http.py:78-104,155-165,194-244; contracts/gate/src/lib.rs:149-309; contracts/registry/src/lib.rs:123-140,141-151,152-191; contracts/reports/src/lib.rs:323-422,425-559,598-660,662-764,808-818; intel/api.py:229-260,261-276,283-302; gate/outlayer.py:58-88,91-127)

## Assets

| Asset | What is protected | Existing control |
|---|---|---|
| Gate funds | NEAR and FT balances held by the Gate. The owner also has a direct withdrawal method. (contracts/gate/src/lib.rs:293-309; contracts/gate/src/policy.rs:231-245) | Agent transfers require an accepted ALLOW and configured caps. Owner withdrawal checks the owner and one yoctoNEAR. (contracts/gate/src/lib.rs:194-210,212-237,293-309; contracts/gate/src/policy.rs:231-245) |
| Verifier key | The live signer reads and uses the key file named by VERIFIER_KEY_FILE; the Gate verifies the verdict signature and time bounds. (gate/agent.py:71-78; gate/signer.py:29-45,58-76; contracts/gate/src/verdict.rs:53-96) | The owner can rotate the current and previous verifier keys and set the previous key's expiry. (contracts/gate/src/policy.rs:163-182) |
| Recorder authority | The registry's configured recorder can write verdict and label records; the owner can replace that account. (contracts/registry/src/lib.rs:123-140,141-151,152-191,192-205,253-259) | Writes require the recorder account; batch length, verdict ID length, and hash formats are checked. Those checks do not verify a Gate signature. (contracts/registry/src/lib.rs:141-151,152-191,253-259,260-291,293-309) |
| Agent key | The Gate registers an agent public key and gives it a function-call access key scoped to request_transfer. (contracts/gate/src/policy.rs:49-92) | The Gate checks that the signer is a registered, enabled agent and enforces denylist and transfer caps. (contracts/gate/src/lib.rs:168-180,212-237) |
| Label store | The local label store contains assertions, source fields, provenance, and supersession links. (intel/labels.py:37-51,53-61,97-130,161-191) | The loader validates row shape, source format, provenance, hashes, and supersession references. These checks do not establish that a source is truthful. (intel/labels.py:97-130,161-191) |

## Entry points

| Entry point | Exposure and existing boundary |
|---|---|
| Agent pay | Obtains or reads a verdict and submits request_transfer only with a structurally valid signed ALLOW; DENY, UNKNOWN, and unsigned ALLOW are not sent. (gate/agent.py:286-361) |
| MCP server | Exposes payment checks, quote preflight, and account scans; tool dispatch rejects malformed and unknown names, and framed messages over 1,048,576 bytes are refused before reading the body. (mcp/server.py:152-185,188-222,225-236,244-279,282-312) |
| HTTP verdict endpoint | Requires a configured API key and rate limit, returns unsigned verdicts, and passes REPORTS_ACCOUNT_ID to the verdict service when set. (gate/http.py:78-104,155-165,194-244) |
| Intel API | Serves health, feed, issuer, search, account, entity, label, incident, evidence, flow, and cluster reads; static paths are confined beneath the selected site root. (intel/api.py:229-260,261-276,283-302) |
| Gate request_transfer | Checks pause state, caller, registered agent, ALLOW, replay use, and caps before scheduling a NEAR or FT transfer. (contracts/gate/src/lib.rs:149-309) |
| Registry recorder methods | record, record_batch, and record_label are recorder-only; batch length, hashes, verdict ID length, and duplicate label assertion hashes are checked. (contracts/registry/src/lib.rs:123-140,141-151,152-191,253-259,260-291,293-309) |
| Reports contract | Writes are submit_report, moderate, dispute, and resolve_dispute; views include report and dispute reads, subject_summary, version, and state_version. (contracts/reports/src/lib.rs:323-422,425-559,598-660,662-764,766-768,777-779,808-818,267-269,271-273,275-277) |

## Actors and threats

| Actor and threat | Mitigation present | Residual risk |
|---|---|---|
| Prompt-injected agent directs a payment to an attacker. | The injection check scans the transfer memo locally and may send that memo to ShieldBot; the payment path sends only a signed ALLOW. (gate/rules.py:501-523; gate/agent.py:286-361) | The scanner receives the memo, not the agent's full prompt or other context. A clean ALLOW with no visible Gate-policy refusal proceeds without human confirmation. **Open.** (gate/rules.py:501-523; gate/verdict.py:103-109; gate/agent.py:286-361) |
| Malicious payee uses a lookalike or newly controlled account. | Non-allowlisted receivers get age, dust, lookalike, and contract-metadata checks; the Gate enforces per-call and window caps. (gate/rules.py:230-243,540-578,581-630,633-771,774-794,847-863; contracts/gate/src/lib.rs:212-237) | Allowlisted receivers skip tier-two checks. A listed payee that turns malicious or is compromised before it is labelled remains within the configured caps. **Open.** (gate/rules.py:860-865; contracts/gate/src/lib.rs:212-237) |
| Malicious token or receiver contract misrepresents its behavior. | FT checks require a catalog or cap token, sane ft_metadata, receiver storage registration, and any configured issuer blacklist checks. Each issuer entry must configure a clear answer: only that exact value and type passes, and the exact banned value and type signals. No clear key, an unexpected value or type, a missing view or an unavailable read gives unknown; signal wins over unknown, which wins over pass. Missing contract source metadata can add a signal only alongside another tier-two signal. (gate/rules.py:376-404,407-477,480-498,633-771,774-794) | These checks do not attest execution behavior. The Gate calls ft_transfer and treats a non-failed promise result as completion; a receiver with contract_source_metadata passes the metadata check without a behavior review. **Open.** (contracts/gate/src/lib.rs:293-309,312-349; gate/rules.py:774-794) |
| Verifier signs an ALLOW with evidence the registry does not contain. | The Gate verifies the verdict signature and binds the evidence hash to the signed message. It does not check that hash against the registry; the registry records verdicts as an audit record, and the Gate trusts its configured verifier key. (contracts/gate/src/verdict.rs:22-47,76-95; contracts/gate/src/lib.rs:194-210; contracts/registry/src/lib.rs:141-191) | A compromised or mistaken verifier can sign an ALLOW with a missing or mismatched evidence record, and the Gate will accept it if the signed transfer and Gate policy checks pass. **Open. Medium. Fix planned after submission.** (contracts/gate/src/lib.rs:194-210) |
| Signed verdict names a malicious or unintended NEP-141 token. | The Gate requires the token in the owner-configured caps for the selected payee category. There is no separate Gate-wide token allowlist or token behavior check, so those caps and the verifier define token trust. (contracts/gate/src/lib.rs:187-192,228-237) | A malicious token can misrepresent transfer success or execute token-specific behavior the Gate does not inspect. **Open. Medium. Fix planned after submission.** (contracts/gate/src/lib.rs:295-300,312-349) |
| Signed memo is expected to affect a native NEAR transfer. | Gate 0.2.2, deployed on testnet on 9 Nov, rejects any present native memo, including an empty string, before signature verification or cap debit. Native NEAR uses a plain Transfer with no memo field. (contracts/gate/src/lib.rs:187-193,305-311; res/BUILD-gate.md:5-7) | **Closed for native payments by the deployed guard.** FT memos remain part of ft_transfer; this does not add arbitrary transaction simulation. (contracts/gate/src/lib.rs:305-311; fixtures/runs/gate-022-deploy-20261109.txt) |
| Compromised operator machine uses credentials or changes local inputs. | The agent access key is scoped to request_transfer; transfer caps, pause, allowlist, and verifier rotation are owner-controlled. The label loader checks content consistency. (contracts/gate/src/policy.rs:49-92,104-115,139-162,163-182,193-198; contracts/gate/src/lib.rs:168-180,212-237; intel/labels.py:97-130,161-191) | An owner key can withdraw a chosen asset amount to a chosen receiver, up to the Gate balance. After the 9 Nov handover the owner key also has FullAccess on the Gate and can replace its code (`fixtures/runs/gate-022-readbacks-20261109.json`). Verifier and agent credentials together can submit transfers within Gate policy. A host writer can recompute label hashes, which do not authenticate source truth. **Open.** (contracts/gate/src/policy.rs:231-245; gate/signer.py:29-45,58-76; gate/agent.py:65-70,286-361; contracts/gate/src/lib.rs:194-210,212-237; intel/labels.py:53-61,161-191) |
| Compromised recorder writes false registry data, including an unsigned ALLOW. | Only the configured recorder can write; batch length, hash format, and label assertion-hash reuse are checked. (contracts/registry/src/lib.rs:123-140,141-151,152-191,253-259,260-291,293-309) | RecordInput has no signature field, record_one stores the supplied verdict without signature or evidence verification, and is_allowed accepts a stored ALLOW. record_label stores caller-supplied fields with a parsed assertion hash without recomputing that hash from the fields. **Open. Medium.** (contracts/registry/src/lib.rs:20-26,152-191,210-223,260-291,293-309) |
| Spam reporter floods reports across multiple submitters. | Reports and disputes require the exact REPORT_DEPOSIT; each submitter is limited to five pending reports. (contracts/reports/src/lib.rs:9,323-422,598-660,853-858) | The pending limit is per submitter, not global, so many submitters can create reports in parallel. **Open. Medium.** (contracts/reports/src/lib.rs:323-422) |
| Moderator accounts share one trust boundary. | The owner configures a distinct moderator list; moderators can moderate reports and resolve disputes. With multiple moderators, an accepting moderator and any accept voter cannot resolve the report's dispute. (contracts/reports/src/lib.rs:302-320,425-559,662-764,945-954) | The 9 Nov testnet demo used three moderator accounts and required two approvals: the owner's vote left the report pending, mod2's second vote accepted it, then mod3 resolved the dispute (`fixtures/runs/reports-threshold-demo-20261109.txt`). All moderator accounts are controlled by the Siyab team. The threshold demo proves the contract rule, not independent review. **Open. Medium.** (contracts/reports/src/lib.rs:425-559,662-764; fixtures/runs/reports-threshold-demo-20261109.txt) |
| A signed ALLOW carries action ask. | The verdict service defaults to signing only action sign, and ordinary pay refuses an ask. The attack harness deliberately requests sign and ask to exercise Gate policy refusals. **Mitigated in ordinary payment. Low.** (gate/verdict.py:61-63,103-109; gate/agent.py:228-234,286-361,386-434) | The verifier is still trusted to sign; the Gate must enforce the visible policy itself. (contracts/gate/src/lib.rs:149-210,212-237) |
| The configured reports contract read fails or is unreachable. | When REPORTS_ACCOUNT_ID is set, a denied report signals DENY, unreadable or malformed summaries become UNKNOWN, and only ALLOW is signed. The HTTP endpoint now passes this setting through. (gate/http.py:78-104,155-165; gate/rules.py:407-477,810-844; intel/reports.py:5-31,34-54; gate/verdict.py:103-109) | An unavailable summary prevents an ALLOW signature. Unsetting REPORTS_ACCOUNT_ID skips this check. **Open. Medium.** (gate/rules.py:407-477; gate/http.py:78-104) |
| Caller floods the read-only Intel API. | Static path resolution rejects targets outside the configured site root. (intel/api.py:261-276) | The GET handler has no authentication or request-rate control, so availability under abusive read traffic is **open**. (intel/api.py:283-302) |
| An OutLayer approval's request_data describes another operation than the one its request_hash covers, and an approver signs the adapter's vote over that hash. | The OutLayer voter adapter judges only a pending NEAR transfer or ft_transfer call in which it reads every field except a call's gas, which it accepts unjudged, abstains on every other operation and on action ask, and signs nothing, sends nothing and reads no key; it returns the vote message for the approver's own key to sign. (gate/outlayer.py:58-88,91-127; docs/OUTLAYER.md:36-53) | The vote message carries the approval's request_hash as given, checked only as a non-empty string: the adapter judges request_data and does not recompute request_hash, because OutLayer does not specify the canonical JSON form it hashes, so an approval whose request_data and request_hash disagree gets a vote on an operation the verdict did not judge. The approver's key signs the vote outside this repository, so its custody is outside this model. Nothing has run against OutLayer. **Open. Medium.** (gate/outlayer.py:91-127; docs/OUTLAYER.md:53,62,66) |
| A 1Click quote verdict is applied to a quote it did not judge: a tampered or stale quote answer, or a later quote whose request differs. | Every quote request is dry; the answer must echo every field sent, the deadline as the same instant, carry the named app fees plus at most the recorded service fee, and set no unknown, non default or unjudged routing key, or quote_dry is a signal (unknown instead when the service fee file cannot be read and the echo adds exactly one unnamed fee); the evidence document records the judged request, with the refund account and refund type the caller names and any app fees it names, and the quote's correlationId, timestamp, amountOut and minAmountOut; verify_binding refuses an answer whose evidence hash, kind or verdict does not check, or a later quote request that leaves out or changes any judged field but dry (the deadline as the same instant, slippage no higher). The CLI and MCP call verify_binding, judge_quote checks at one clock reading after its last external read that the quote timestamp is no more than 300000 ms old and that the judged deadline is after it (quote_deadline), verify_binding refuses an ALLOW whose judged deadline is not after one reading of its own clock or whose quote is then more than 300000 ms old, and a document that predates request binding, every quote request (the caller's before any request, the dry echo, the later request and the status request) is held to the recorded request schema and the dry answer to the answer schema, every deadline must be a complete date-time with an explicit zone, and a supplied deposit address needs the caller's refund account and is checked against the request returned by 1Click status: dry false, every judged field equal (refundTo, refundType, swapType and depositType included), slippageTolerance no higher, appFees equal to the named ones, no virtual chain, custom message or rebate field, the default deposit mode, insurance and confidentiality, no key the check does not know, a request the schema allows, a real quote in the status answer whose deadline and timestamp are complete date-times with an explicit zone and whose depositAddress is exactly the supplied address, a status answer status in DEPOSIT_STATUSES, which is empty because no recorded source lists the 1Click status values, so a supplied address never passes yet, and a status deadline, real quote deadline, real quote age, judged deadline and quote age that hold at one clock reading after the status read (each deadline after it, each timestamp no more than 300000 ms old and not in the future), or the status check is UNKNOWN. (gate/intents.py:118-161,215-238,287-491,494-590,592-658,661-743,746-797,924-953; gate/__main__.py:133-175; mcp/server.py:188-222; docs/API.md:215-217,222) | The answer is unsigned, so a caller able to replace the whole answer and recompute its hash can forge it, and the 1Click answer's own signature is not verified because no verifying key is recorded. The request binding, age limit and supplied-address status lookup do not authenticate a forged server response. No live status answer is recorded, so the status key list comes from the published request schema and the recorded dry echo, and a real quote with an app fee 1Click adds on its own is refused unless the caller names that fee too. Neither the status answer's status key nor its values are recorded, so no status value is accepted and a supplied deposit address always makes the status check UNKNOWN; the tests reach a status pass only with a synthetic accepted value. **Open. Medium.** (gate/intents.py:592-797,924-953; gate/__main__.py:133-175; mcp/server.py:188-222; tests/test_intents.py:1-3,268-1373,1374-1691; docs/API.md:217,222,224,225) |

## Closed on main

| Closed threat | Fix on main |
|---|---|
| A report submitter moderates their own report; duplicate moderators or same-moderator review bypass distinct review. | moderate rejects the report submitter, moderator configuration rejects duplicate accounts, and the moderator who accepted a decision cannot resolve its dispute when more than one moderator is configured. (contracts/reports/src/lib.rs:302-320,425-559,662-764,945-954) |
| Reports or disputes accept a non-exact deposit. | Both write paths call the shared check, which requires attached deposit to equal REPORT_DEPOSIT. (contracts/reports/src/lib.rs:9,323-422,598-660,853-858) |
| Pending reports change a payment verdict. | A pending-only summary has no effect; the configured verdict path uses that summary. (intel/reports.py:34-54; gate/rules.py:407-477) |
| A DENY can cite a newer social report instead of the deny report. | subject_summary exposes latest_deny_id and the reports effect uses that field for DENY. (contracts/reports/src/lib.rs:808-818,899-909; intel/reports.py:34-45) |
| Repeated upheld disputes exhaust a report's lifetime dispute cap. | Reports 0.1.3 has no lifetime cap and checks only the last dispute to prevent a second concurrently open dispute; the regression test permits an eighth dispute after seven non-overturning resolutions. Testnet runs Reports 0.1.3 since the 9 Nov redeploy (`contracts/reports/Cargo.toml:3`; `contracts/reports/src/lib.rs:598-660,2370-2405`; `res/BUILD-reports.md:5,7`; `fixtures/runs/reports-013-deploy-20261109.txt`). |
| Used-verdict storage grew without automatic pruning, and a verdict could be issued far in the future. | Source version 0.2.0 prunes up to four expired used verdicts per request, stops at a live queue head, and rejects issued_ms more than 30,000 ms ahead. Testnet runs Gate 0.2.2 since the 9 Nov redeploy (`res/BUILD-gate.md`). (contracts/gate/Cargo.toml:3; contracts/gate/src/lib.rs:65-93,149-158; contracts/gate/src/verdict.rs:53-96; res/BUILD-gate.md:5,7; docs/TESTNET.md:32) |
| The HTTP verdict endpoint skipped the configured reports check. | The endpoint reads REPORTS_ACCOUNT_ID at startup and passes it to the verdict request. When set, the rules include the community report check. (gate/http.py:78-104,155-165; gate/rules.py:407-477) |
| Equal approval thresholds can leave every moderator barred from resolving an accepted report's dispute. | `set_approvals_required` refuses a threshold equal to the moderator count, and `set_moderators` refuses a list equal to a threshold above 1. The unit tests prove both refusals; the sandbox round trip files and resolves a dispute with the free moderator. (contracts/reports/src/lib.rs:284-320,1392-1417; contracts/reports/tests/sandbox.rs:433-704) |
