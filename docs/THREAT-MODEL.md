# Threat model

This model follows the NEAR payment path through the agent, verdict service and Gate contract, and the recorder path through the registry contract. (`gate/agent.py:200-223`, `contracts/gate/src/lib.rs:68-223`, `contracts/registry/src/lib.rs:123-189`)

## Assets

| Asset | What is protected | Existing control |
|---|---|---|
| Gate funds | NEAR and FT transfers are sent from the Gate account; the owner also has a direct `withdraw` method for either asset. (`contracts/gate/src/lib.rs:209-216`, `contracts/gate/src/policy.rs:172-185`) | Agent transfers require a valid verdict and configured caps; owner withdrawal requires the owner account and one yoctoNEAR. (`contracts/gate/src/lib.rs:110-179`, `contracts/gate/src/policy.rs:17-23,172-185`) |
| Verifier key | The live signer reads the secret from the file named by `VERIFIER_KEY_FILE`; the Gate stores current and optional previous verifier public keys. (`gate/signer.py:29-44,58-75`, `contracts/gate/src/lib.rs:26-34`) | The Gate checks the signature, expiry, TTL and key id; the owner can rotate verifier keys and bound the previous key's validity. (`contracts/gate/src/verdict.rs:53-94`, `contracts/gate/src/policy.rs:139-157`) |
| Recorder key | The recording script resolves the recorder account key under `NEAR_KEYS_DIR` and signs `record_batch` and `record_label` transactions. (`scripts/lib.sh:62-64`, `scripts/record_verdicts.sh:20-21,49-54`) | The registry permits those write methods only from its configured recorder account, and the owner alone can change that account with one yoctoNEAR. (`contracts/registry/src/lib.rs:152-162,191-204,252-258`) |
| Agent key | The Gate records each agent public key and installs a function-call access key limited to `request_transfer`; the agent transport loads the corresponding secret key to submit that call. (`contracts/gate/src/policy.rs:35-72`, `gate/agent.py:65-68,91-106,132-145`) | The Gate checks the transaction signer against a registered, enabled agent and applies allowlist, denylist and asset caps. (`contracts/gate/src/lib.rs:73-109,129-167`) |
| Label store | `intel/labels.jsonl` is the default local store and each loaded row is validated, including its assertion hash and provenance fields. (`intel/labels.py:14-27,94-126,158-187`) | Row shape, source format, provenance, supersession links and inferred refusal labels are checked on load. (`intel/labels.py:65-126,158-187`) |

## Entry points

| Entry point | Exposure and existing boundary |
|---|---|
| `gate/agent.py:pay` | Loads an optional verdict file or obtains a verdict, records evidence, and submits only a signed ALLOW to `request_transfer`; ask outcomes are recorded without submission. (`gate/agent.py:275-337`) |
| MCP server tools | `tools/call` dispatches `check_near_payment`, `check_intents_quote` and `scan_near_account`; live payment checks can sign an ALLOW, while the quote tool is an unsigned preflight. (`mcp/server.py:49-92,143-174,177-198,209-242`) |
| Intel API routes | `route` serves health, feed, issuers, search, account, entity, label, incident, evidence, flow and cluster reads; the HTTP handler implements `GET`, and static paths are confined beneath the selected site directory. (`intel/api.py:229-258,261-275,282-312`) |
| Gate `request_transfer` | Requires an unpaused Gate, the Gate as predecessor, a registered enabled signer, a valid request, an ALLOW verdict, and available cap; it consumes the verdict id and cap before scheduling NEAR or FT transfer. (`contracts/gate/src/lib.rs:68-179,209-223`) |
| Registry recorder methods | `record`, `record_batch` and `record_label` are recorder-only; the batch has a maximum size, verdict evidence hashes are format-checked, and label assertion hashes cannot be reused. (`contracts/registry/src/lib.rs:123-189,252-307`) |
| Reports contract on `build/r1-reports` | `submit_report`, `moderate`, `dispute` and `resolve_dispute` are the write paths; report and dispute reads are exposed through view methods. (`build/r1-reports:contracts/reports/src/lib.rs:234-399,438-556,558-607`) |

## Actors and threats

| Actor and threat | Mitigation present | Residual risk |
|---|---|---|
| Prompt-injected agent directs a payment to an attacker. | The memo check looks for instruction-shaped patterns and combines them with the optional ShieldBot scan; DENY does not receive a verdict, UNKNOWN asks a human, and `pay` submits a signed ALLOW only. (`gate/rules.py:400-422`, `gate/verdict.py:99-115`, `gate/agent.py:288-323`) | The scanner receives the transfer memo, not the agent's full prompt or other context; a clean ALLOW with no Gate-policy refusal proceeds automatically. A malicious instruction that produces a valid transfer can therefore pass if it is not represented in the memo or checks. **Open.** (`gate/rules.py:400-422`, `gate/agent.py:288-323`) |
| Malicious payee uses a lookalike or a newly controlled account. | The verdict path checks labels, account existence, lookalikes, age, dust funding and contract metadata for non-allowlisted receivers; unknown-payee transfers require configured caps, and the Gate enforces per-call and window caps. (`gate/rules.py:319-376,425-571,634-655`, `contracts/gate/src/lib.rs:93-97,129-167`) | Tier-two age, lookalike, dust and contract checks are skipped for allowlisted receivers; an allowed payee that turns malicious or whose compromise is not yet labelled remains within the configured caps. **Open.** (`gate/rules.py:634-655`, `contracts/gate/src/lib.rs:93-97,129-167`) |
| Malicious token or receiver contract lies about its behavior. | FT verdict checks require a catalog or cap token, sane `ft_metadata`, receiver storage registration and, on mainnet when configured, issuer blacklist reads; the receiver code check can flag contract code without source metadata alongside another signal. (`gate/rules.py:293-316,353-397,574-594`) | These checks do not attest token execution semantics: the Gate calls the token's `ft_transfer` and its callback treats a successful promise result as success. A receiver contract with source metadata also passes the code check, which does not review its behavior. **Open.** (`contracts/gate/src/lib.rs:209-223,225-245`, `gate/rules.py:574-594`) |
| Compromised operator machine uses locally available credentials or changes local inputs. | The agent key created by the Gate is limited to `request_transfer`; transfer policy, caps, pause and verifier rotation remain owner-controlled, and the local label loader rejects malformed or inconsistent rows. (`contracts/gate/src/policy.rs:17-23,35-82,86-170`, `intel/labels.py:94-126,158-187`) | If the machine can read the owner key, `withdraw` can transfer an arbitrary requested amount of either asset; if it can read verifier and agent secrets, it can sign and submit transfers still bounded by Gate policy. Label hashes are recomputable and do not authenticate the truth of a source. **Open.** (`contracts/gate/src/policy.rs:172-185`, `gate/signer.py:29-44,58-75`, `gate/agent.py:65-76,91-106`, `intel/labels.py:53-57,94-126`) |
| Compromised recorder key writes false registry data. | Only the configured recorder account can call recording methods; batches are bounded, evidence and assertion hashes must be lowercase 64-character hex, and duplicate label assertion hashes are refused. (`contracts/registry/src/lib.rs:141-177,252-307`) | The recorder path does not verify a recorded verdict's Gate signature or evidence contents, and `record_label` does not prove that its label fields are committed by the supplied assertion hash; a compromised recorder can therefore corrupt the registry's record. **Open.** (`contracts/registry/src/lib.rs:141-177,260-307`) |
| Spam reporter floods the reports contract on `build/r1-reports`. | Each report requires the configured deposit, an account-id subject, a valid evidence hash and HTTPS URL, and each submitter can have at most five pending reports. (`build/r1-reports:contracts/reports/src/lib.rs:8-12,245-266,718-735`) | The pending limit is counted per submitting account, so multiple accounts can submit in parallel; there is no global submission limit in this path. **Open.** (`build/r1-reports:contracts/reports/src/lib.rs:260-266,302-320`) |
| Hostile or compromised report moderator accepts false reports or suppresses valid ones. | Only owner-selected moderators can moderate, each call requires one yoctoNEAR and a valid reason hash, and accepted reports can be disputed and then restored or overturned by a moderator. (`build/r1-reports:contracts/reports/src/lib.rs:234-243,345-399,438-460,506-555,617-629`) | One listed moderator can decide a pending report; the contract validates the reason hash's shape but does not establish the truth of report evidence or require an independent second moderator. **Open.** (`build/r1-reports:contracts/reports/src/lib.rs:345-379,617-629,718-735`) |
| Caller floods the read-only Intel API. | The route exposes GET reads and static path resolution rejects targets outside the configured site root. (`intel/api.py:229-258,261-275,282-312`) | The handler has no authentication or request-rate control, so availability under abusive read traffic is **open**. (`intel/api.py:282-312`) |

## Open items ranked by severity

| Rank | Severity | Open item | Source |
|---:|---|---|---|
| 1 | High | Owner-key compromise permits an uncapped withdrawal of a chosen NEAR or FT amount to a chosen receiver. (`contracts/gate/src/policy.rs:17-23,172-185`) | `contracts/gate/src/policy.rs:17-23,172-185` |
| 2 | High | A compromised host with both verifier and agent credentials can authorize and submit transfers up to the active Gate policy caps. (`gate/signer.py:29-44,58-75`, `gate/agent.py:65-76,91-106`, `contracts/gate/src/lib.rs:110-167`) | `gate/signer.py:29-44,58-75`; `gate/agent.py:65-76,91-106`; `contracts/gate/src/lib.rs:110-167` |
| 3 | High | A malicious FT token can misrepresent transfer success, and a receiver contract with source metadata is not behaviorally audited. (`contracts/gate/src/lib.rs:209-245`, `gate/rules.py:574-594`) | `contracts/gate/src/lib.rs:209-245`; `gate/rules.py:574-594` |
| 4 | High | Prompt injection outside the memo can cause a clean, allowlisted transfer to proceed without a human confirmation step. (`gate/rules.py:400-422`, `gate/agent.py:288-323`) | `gate/rules.py:400-422`; `gate/agent.py:288-323` |
| 5 | High | A malicious allowlisted payee skips tier-two age, lookalike, dust and contract checks; Gate caps limit but do not eliminate the permitted loss. (`gate/rules.py:634-655`, `contracts/gate/src/lib.rs:129-155`) | `gate/rules.py:634-655`; `contracts/gate/src/lib.rs:129-155` |
| 6 | Medium | Local label row hashes verify content consistency but do not authenticate the truth or provenance of the source; a host writer can recompute row ids. (`intel/labels.py:53-57,94-126,158-187`) | `intel/labels.py:53-57,94-126,158-187` |
| 7 | Medium | A compromised recorder can write unauthenticated verdict and label records that pass the registry's shape checks. (`contracts/registry/src/lib.rs:141-177,252-307`) | `contracts/registry/src/lib.rs:141-177,252-307` |
| 8 | Medium | A hostile moderator can make a unilateral report decision; dispute resolution uses the same moderator role. (`build/r1-reports:contracts/reports/src/lib.rs:345-399,506-555,617-629`) | `build/r1-reports:contracts/reports/src/lib.rs:345-399,506-555,617-629` |
| 9 | Medium | Report deposits and per-account pending limits do not stop Sybil submission across many accounts. (`build/r1-reports:contracts/reports/src/lib.rs:8-9,245-266,302-320`) | `build/r1-reports:contracts/reports/src/lib.rs:8-9,245-266,302-320` |
| 10 | Low | The Intel API can be read without authentication or rate control, leaving request-volume denial of service open. (`intel/api.py:282-312`) | `intel/api.py:282-312` |
