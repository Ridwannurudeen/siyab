# Threat model

This model covers the NEAR agent payment path, the MCP and HTTP verdict interfaces, the Gate, registry recording, reports, read-only Intel API, unsigned mainnet account, token and proposed-transaction checks, the OutLayer approver adapter, NEAR wallet sign-in and the encrypted personal workspace, cross-origin public reads, the local 1Click settlement command and the reference check adapters. ## Entry points

| Entry point | Exposure and existing boundary |
|---|---|
| Agent pay | Obtains or reads a verdict and submits request_transfer only with a structurally valid signed ALLOW; DENY, UNKNOWN, and unsigned ALLOW are not sent. (gate/agent.py:287-366) |
| MCP server | Exposes payment checks, quote preflight, account scans, and the unsigned `check_near_account`, `check_near_token` and `check_near_transaction` tools; tool dispatch rejects malformed and unknown names, and framed messages over 1,048,576 bytes are refused before reading the body. (mcp/server.py:197-230,233-267,270-318,326-373,376-406) |
| Unsigned mainnet checks | `SIYAB_CHECKS=1` enables the three MCP checks and `GET /live/account-check/<account>` and `GET /live/token-check/<token>`; disabled MCP calls refuse and disabled public routes return 404. `/live/health` exposes a `checks` boolean. The live routes share request budgets, deadlines, bounded caching and input validation. The transaction check is offline and MCP only. Every answer has `signing: "never"` and no signed verdict; none reaches the live signer. (`mcp/server.py:_require_checks`; `mcp/server.py:_check_near_account`; `mcp/server.py:_check_near_token`; `mcp/server.py:_check_near_transaction`; `intel/live.py:handle`; `intel/live.py:_read`; `intel/live.py:_route`; `intel/live.py:ROUTE_COSTS`) |
| HTTP verdict endpoint | Requires a configured API key and rate limit, returns unsigned verdicts, and passes REPORTS_ACCOUNT_ID to the verdict service when set. (gate/http.py:78-104,155-165,194-244) |
| Intel API | Serves health, feed, issuer, search, account, entity, label, incident, evidence, flow, and cluster reads; static paths are confined beneath the selected site root. (intel/api.py:252-283,284-300,360-401) |
| Gate request_transfer | Checks pause state, caller, registered agent, ALLOW, replay use, and caps before scheduling a NEAR or FT transfer. (contracts/gate/src/lib.rs:155-336) |
| Registry recorder methods | record, record_batch, and record_label are recorder-only; batch length, hashes, verdict ID length, and duplicate label assertion hashes are checked. (contracts/registry/src/lib.rs:123-140,141-151,152-191,253-259,260-291,293-309) |
| Reports contract | Writes are submit_report, moderate, dispute, and resolve_dispute; views include report and dispute reads, subject_summary, version, and state_version. (contracts/reports/src/lib.rs:323-422,425-559,598-660,662-764,766-768,777-779,808-818,267-269,271-273,275-277) |
| NEAR wallet sign-in and vault | `POST /workspace-api/near/challenge` and `verify` each allow five requests per minute per workspace client bucket; persisted challenge and access key lookup caps apply per IPv4 /32 or IPv6 /48. Vault writes need the wallet session, CSRF and exact Origin. (`intel/workspace_api.py:77-111`; `intel/private_workspace.py:73-155`; `intel/near_auth.py:17-24,81-90,137-197,209-233`) |
| Cross-origin public reads | GET and HEAD on `_PUBLIC_CORS_PATH` routes carry `Access-Control-Allow-Origin: *` without credentials; other OPTIONS answer 403 `cors_forbidden`. (`intel/api.py:86-91,405-420,477-480`) |
| 1Click settlement CLI | Operator-run on mainnet; signs only with `--deposit` and an external FullAccess key file. (`gate/__main__.py:402-426`; `gate/oneclick.py:759-972`) |

## Actors and threats

| Actor and threat | Mitigation present | Residual risk |
|---|---|---|
| Prompt-injected agent directs a payment to an attacker. | The injection check scans the transfer memo locally and may send that memo to ShieldBot; the payment path sends only a signed ALLOW. (gate/rules.py:523-545; gate/agent.py:287-366) | The scanner receives the memo, not the agent's full prompt or other context. A clean ALLOW with no visible Gate-policy refusal proceeds without human confirmation. **Open.** (gate/rules.py:523-545; gate/verdict.py:103-112; gate/agent.py:287-366) |
| Malicious payee uses a lookalike or newly controlled account. | Non-allowlisted receivers get age, dust, lookalike, and contract-metadata checks; the Gate enforces per-call and window caps. An unresolved archival age probe uses a bounded block-time search around the reference block's 7-day cutoff: a young signal from boundary-block absence at B requires adjacent existing B/Y blocks, with `Y.header.prev_hash == B.header.hash`, and exact receiver and height metadata; `UNKNOWN_BLOCK` is no proof of a skip. Failed reads, unproven gaps, read caps and deadline expiry leave age unknown. (gate/rules.py:252-265,567-652,655-767,770-822,825-973,976-996,1053-1099; contracts/gate/src/lib.rs:238-263) | Allowlisted receivers skip tier-two checks. A listed payee that turns malicious or is compromised before it is labelled remains within the configured caps. Point probes cannot prove continuity: an account deleted and re-created within 7 days by someone else can pass on the old account's history, a pre-existing limit that this boundary search widens to first accounts 7 to about 14 days old. **Open.** (gate/rules.py:1053-1099; contracts/gate/src/lib.rs:238-263) |
| Malicious token or receiver contract misrepresents its behavior. | FT checks require a catalog or cap token, sane ft_metadata, receiver storage registration, and any configured issuer blacklist checks. Each issuer entry must configure a clear answer: only that exact value and type passes, and the exact banned value and type signals. No clear key, an unexpected value or type, a missing view or an unavailable read gives unknown; signal wins over unknown, which wins over pass. Missing contract source metadata can add a signal only alongside another tier-two signal. (gate/rules.py:398-426,429-499,502-520,825-973,976-996) | These checks do not attest execution behavior. The Gate calls ft_transfer and `on_transfer` (`contracts/gate/src/lib.rs:348-385`) treats a non-failed promise result as completion; a receiver with contract_source_metadata passes the metadata check without a behavior review. **Open.** (contracts/gate/src/lib.rs:332-345,348-385; gate/rules.py:976-996) |
| A caller treats an unsigned check or a recorded result as live payment authorization. | The three MCP checks and both live check routes return `verdict: null` and `signing: "never"`. MCP account and token replay text identifies recorded fixtures (replay) and the recorded block. Public wording maps ALLOW to "No flag found", DENY to "Flagged" and ASK to "Not enough data"; a clean proposed transaction means only "no modelled risk found". Unknown or partial data cannot pass. (`mcp/server.py:handle`; `gate/account_check.py:check_account`; `gate/token_check.py:check_token`; `gate/txcheck.py:check_transaction`) | Evidence is unsigned and covers only modelled checks and available sources. MCP account checks use fixed mainnet, NearBlocks and archival endpoints and inherit fixture mode. Live account checks use mode `off`, honor mainnet and archival overrides, and read NearBlocks only when explicitly enabled. Both token interfaces use the fixed mainnet endpoint and ignore `NEAR_MAINNET_RPC_URL`; the live token route uses mode `off`. These boundaries do not authenticate a whole answer replaced by a caller. **Open.** (`mcp/server.py:_check_near_account`; `mcp/server.py:_check_near_token`; `intel/live.py:_route`; `gate/token_check.py:_mainnet`) |
| Verifier signs an ALLOW with evidence the registry does not contain. | The Gate verifies the verdict signature and binds the evidence hash to the signed message. It does not check that hash against the registry; the registry records verdicts as an audit record, and the Gate trusts its configured verifier key. (contracts/gate/src/verdict.rs:22-47,95-109; contracts/gate/src/lib.rs:200-236; contracts/registry/src/lib.rs:141-191) | A compromised or mistaken verifier can sign an ALLOW with a missing or mismatched evidence record, and the Gate will accept it if the signed transfer and Gate policy checks pass. **Open. Medium.** Gate source 0.3.0 adds an attested mode that accepts verdicts only from enclave keys synced from a pinned registry under owner-approved measurements (`contracts/gate/src/attested.rs:172-405`). It is not deployed, and testnet runs Gate 0.2.2 (`res/BUILD-gate.md:7`), so operator verifier trust stays open on every deployed Gate. Attested key verification would still not prove the evidence hash has a verdict-registry record (`contracts/gate/src/verdict.rs:66-110`). |
| Signed verdict names a malicious or unintended NEP-141 token. | The Gate requires the token in the owner-configured caps for the selected payee category. There is no separate Gate-wide token allowlist or token behavior check, so those caps and the verifier define token trust. (contracts/gate/src/lib.rs:193-198,254-263) | A malicious token can misrepresent transfer success or execute token-specific behavior the Gate does not inspect. **Open. Medium. Fix planned after submission.** (contracts/gate/src/lib.rs:332-345,348-385) |
| Signed memo is expected to affect a native NEAR transfer. | Gate 0.2.2, deployed on testnet on 9 Nov, rejects any present native memo, including an empty string, before signature verification or cap debit. Native NEAR uses a plain Transfer with no memo field. (contracts/gate/src/lib.rs:193-199,332-338; res/BUILD-gate.md:5-7) | **Closed for native payments by the deployed guard.** FT memos remain part of ft_transfer; this does not add arbitrary transaction simulation. (contracts/gate/src/lib.rs:332-338; fixtures/runs/gate-022-deploy-20261109.txt) |
| Compromised operator machine uses credentials or changes local inputs. | The agent access key is scoped to request_transfer; transfer caps, pause, allowlist, and verifier rotation are owner-controlled. The label loader checks content consistency. (contracts/gate/src/policy.rs:49-92,104-115,139-162,163-183,194-199; contracts/gate/src/lib.rs:174-186,238-263; intel/labels.py:97-130,161-191) | An owner key can withdraw a chosen asset amount to a chosen receiver, up to the Gate balance. Verifier and agent credentials together can submit transfers within Gate policy. A host writer can recompute label hashes, which do not authenticate source truth. **Open.** (contracts/gate/src/policy.rs:232-246; gate/signer.py:29-45,58-76; gate/agent.py:65-70,287-366; contracts/gate/src/lib.rs:200-236,238-263; intel/labels.py:53-61,161-191) |
| Compromised recorder writes false registry data, including an unsigned ALLOW. | Only the configured recorder can write; batch length, hash format, and label assertion-hash reuse are checked. (contracts/registry/src/lib.rs:123-140,141-151,152-191,253-259,260-291,293-309) | RecordInput has no signature field, record_one stores the supplied verdict without signature or evidence verification, and is_allowed accepts a stored ALLOW. record_label stores caller-supplied fields with a parsed assertion hash without recomputing that hash from the fields. **Open. Medium.** (contracts/registry/src/lib.rs:20-26,152-191,210-223,260-291,293-309) |
| Spam reporter floods reports across multiple submitters. | Reports and disputes require the exact REPORT_DEPOSIT; each submitter is limited to five pending reports. (contracts/reports/src/lib.rs:9,323-422,598-660,853-858) | The pending limit is per submitter, not global, so many submitters can create reports in parallel. **Open. Medium.** (contracts/reports/src/lib.rs:323-422) |
| Moderator accounts share one trust boundary. | The owner configures a distinct moderator list; moderators can moderate reports and resolve disputes. (contracts/reports/src/lib.rs:302-320,425-559,662-764,945-954) | The 9 Nov testnet demo used three moderator accounts and required two approvals: the owner's vote left the report pending, mod2's second vote accepted it, then mod3 resolved the dispute (`fixtures/runs/reports-threshold-demo-20261109.txt`). (contracts/gate/src/lib.rs:155-236,238-263) |
| The configured reports contract read fails or is unreachable. | When REPORTS_ACCOUNT_ID is set, a denied report signals DENY, unreadable or malformed summaries become UNKNOWN, and only ALLOW is signed. (gate/http.py:78-104,155-165; gate/rules.py:429-499,1013-1050; intel/reports.py:5-31,34-54; gate/verdict.py:103-112) | An unavailable summary prevents an ALLOW signature.
