## Source notes

- NearBlocks supplies explorer and account data. Its free plan is for personal use, and its terms prohibit third party apps from interacting with the service without prior written consent; none was sought or given. The source is a fallback whose terms are under review. The footer attribution is `Data: NearBlocks`.
- GoPlus supplies the address security response used by the EVM preflight.
- 1Click supplies the recorded dry quote. No deposit was made.
- FastNEAR supplies the RPC, archival RPC and transfer reads used here. Its [pricing and limits](https://docs.fastnear.com/pricing) describe credits, plan rate limits, HTTP 402 for exhausted credit and HTTP 429 for rate limiting. Terms of service for these interfaces remain unverified.
- `mainnet.neardata.xyz` supplies read-only NEAR data.
- The feed follower reads finalized heights sequentially from `mainnet.neardata.xyz`. It takes the final height's block from its read of the final block instead of fetching that height again, and once it reaches the final height it waits 1 second before it reads the final block again, so a follower that keeps up makes about one request per height. When `FASTNEAR_API_KEY_FILE` is set and the shared budget permits it, block reads carry the key under caller class `feed`, capped at 120,000 keyed calls per UTC day with no hourly or minute cap. The minimum interval between request starts is 0.1 seconds keyed and 0.4 seconds keyless; response time counts toward that interval, including internal retries. Each attempt is paced and reserved separately, so a retry rechecks the cap and cooldown before sending the key. An absent key, spent cap or shared cooldown sends that request keylessly. Keyed HTTP 401, 402, 403 or 429 retries the same read keylessly, and 402, 403 or 429 start the shared 15 minute key cooldown. The next eligible read uses the key again after the UTC day resets or cooldown ends. State and event blocks stay under `FEED_STATE_DIR`; the budget file is shared with the other readers through `SIYAB_PROVIDER_BUDGET_DB`. The supplied 23 Nov VPS measurements found about 14 heights a minute keyless, about 66 new blocks a minute and about 195 heights a minute keyed. Those observations, not a provider guarantee, explain the cap and fallback (`docs/RUNBOOK.md`, Capped keyed block feed). It stamps `updated_at` in its state at every height and at every read of the final height while it waits there, and, once its run has done either, after every transfer request; a run that has done neither, such as a restart whose first block fetch fails, never moves it. The read only API's `/feed` route and live feed page say the follower stopped, with its last update time and the lag unknown, once that stamp is more than 1600 seconds old; a state without one is judged by `last_time`, the time of the last height it walked, else by `started_at`, when the follower first started, and never by the state file's modification time, which the transfer poll rewrites. A follower event's `block_fixture` names a file under `<state dir>/event-blocks/`, or a key of a feed snapshot's `event_blocks`. A feed snapshot holds the state without its fresh accounts, the event documents and the blocks that raised them. The committed snapshot `intel/feed/follow-snapshot.json` was copied from the hosted follower's state on 4 Nov: following since 2026-11-03T18:55:31Z, 64697 blocks up to height 222975380 (2026-11-04T05:22:06Z), 102 skipped heights and 0 events; the counts block's feed line reads it.
- The feed follower starts a new FastNEAR Transfers API window every 600 seconds once the previous window is complete, making at most one eligible request per block-loop invocation with a local 0.4 second minimum interval, for outgoing transfers from current incident and denylist accounts, with a minimum USD amount filter and system transfers omitted. The API reports an outbound transfer with a negative USD amount; the follower keeps a row when that amount is at least 1000 USD in magnitude, publishes the magnitude with the direction "outbound", and counts the rows it cannot read, such as one without a USD amount, in the state. Each window freezes its end time when it starts, and the next starts at that end, so completed windows are contiguous; it reads up to 20 pages per account and window, and the follower state records a window that reached that cap and the time, status and type of the last failed poll. A 429 retains the same subject, page and resume token until the uncapped Retry-After seconds or HTTP date (60 seconds if absent or invalid); the block walk continues instead of sleeping through the batch or cooldown. Pending rows, page counts and resume tokens stay in memory, and no rows are published or completed cursor advanced until every subject finishes its bounded poll. On restart, the window is replayed from the persisted completed cursor or initial anchor. The field last_large_transfer_completed_ms records actual completion; the initial cursor alone does not. It always polls keylessly and never reads the file named by `FASTNEAR_API_KEY_FILE`, as in the keyless [Transfers API examples](https://github.com/fastnear/transfers-api). HTTP 401, 402 or 403 marks the signal temporarily unavailable in the state; only a complete successful poll clears that status, while the last failed poll remains as history.
- The block stream reports successful contract deployments on current catalog token, infrastructure, bridge, treasury, organisation and watch accounts, including the deployed code hash.

The signature is pure Ed25519 over the sha256 digest of the canonical message; it is not Ed25519ph.

## Follower first-seen index

The follower writes first_seen.sqlite3 beside state.json in FEED_STATE_DIR using the blocks it already reads, with no additional requests. A successful explicit CreateAccount receipt records the receiver, block height, nanosecond timestamp, predecessor, sum of that receipt's Transfer deposits in yoctoNEAR, receipt id and block hash. Recorded block 222139030 contains a named creation with a zero deposit. The first recorded creation per account is retained; this is not proof that an account was never deleted and recreated before observation began.

state.json last_height is the follower's only cursor, read and written as before; restart resumes at last_height + 1. SQLite stores only first-seen rows and inclusive covered height ranges. The index opens in WAL mode with a five-second busy timeout, so an open reader transaction does not block the follower's commit. For each processed height, creation rows and its coverage extension commit in one SQLite transaction before the normal state.json write. Re-applying a block adds no duplicate rows and does not change coverage, so a crash between those writes simply re-applies the block on restart. Null slots do not update last_height, matching the existing follower behavior, and may be read again after restart.

Index SQLite and operating-system errors never stop the follower: the index transaction rolls back, the failed height stays uncovered and the normal state.json cursor write proceeds. A lookup without creation evidence over that gap returns unknown. state.json first_seen_error records the failed height, exception class and a fixed filename-only message, with no external paths or raw exception text. Successful advances retain the last error for diagnosis; coverage ranges show which later heights were indexed. Restart follows the JSON cursor rather than replaying the failed height, so this index failure cannot cause an already-sent block alert to repeat.

An explicit neardata null answer at or below the final height is a skipped block slot: it executes no receipts and counts as covered when its index advance succeeds. HTTP 404 answers, other read errors, processing errors and unprocessed heights leave gaps. A 404 is still listed in skipped_heights as before; other block read or processing errors stop the walk and are retried on restart. Existing follower history is not assumed covered when the index is first installed. Rolling back to code without the index leaves SQLite untouched: heights walked by that code stay outside coverage after re-upgrading, and the follower still resumes at state.json last_height + 1.

The API in `intel/first_seen.py` is `lookup(account_id, from_height, to_height)`, with explicit inclusive bounds and an optional state_dir keyword selecting the index directory. A recorded creation at or before to_height returns created with block evidence, even if it predates from_height or the window contains gaps. A named-account miss returns not_created_in_covered only when every height in [from_height, to_height] is covered; this says nothing about existence before that window. Missing indexes, unreadable indexes, gaps and windows outside coverage return unknown. There is no integer-only or "now" form. covered_ranges reports the processed inclusive ranges.

Implicit creation cannot be distinguished from later transfers using the committed reduced fixtures. A transfer-only receipt to a hex account never becomes creation evidence, and a miss for a 64-hex or 0x-prefixed implicit account remains unknown even within covered heights. NEP-616 deterministic accounts created through state init, whose ids start with 0s followed by hex, do not emit CreateAccount; their misses also remain unknown within covered heights. Real raw implicit-creation data and its distinguishing marker remain unverified offline. This index is not yet used by account_age or dust_funded; rule wiring belongs to part 2.

## Full access key outflow review

`full_access_key_then_outflow` is a candidate signal that needs no label. It fires when a successful full access `AddKey` is added to an account outside `fresh_accounts`, in a receipt without `CreateAccount`, and a successful native `Transfer` of at least 1 NEAR or `DeleteAccount` follows from that account within 10 minutes. The window uses block timestamp milliseconds. Pending key additions persist across blocks and are pruned by timestamp, so skipped heights do not extend the window. The signal stays off the alert path while its false positive rate is unmeasured.

The event destination class is `fresh_dust_funded` when the destination is in `fresh_accounts`, meaning it was created within 24 hours with a deposit below 0.1 NEAR; `implicit` for a 64 hex account id; and `other` otherwise. The class is review metadata and does not affect whether the event fires. Events also record the key, drain kind, whether a different key was removed during the window, amount in yoctoNEAR (null for `DeleteAccount`), block, receipt and source mode.

The reduced block retains `DeleteKey` public keys and `DeleteAccount` beneficiaries. Reduced fixtures from before action reducer version 2 cannot raise this signal. Function call arguments are not retained, so token drains through `ft_transfer` are not visible. The source mode is `replay` for recorded runs and `follow` for the follower.

Run `python -m intel feed-fprate --events <dir> --state <state.json> [--since <height>] [--until <height>] [--review <csv>]` to create or update the review CSV. Event rows and review rates use the selected height range; funnel totals come from the supplied state. Re-running preserves each filled review. Mark `true_positive` only with corroboration: the subject or destination later receives a label, a public incident page names it, or the account holder confirms it. Mark `false_positive` only with a visible benign explanation: the earlier key remains and activity is normal for seven days, or the funds were returned. Otherwise mark `unclear`. For each reviewed stratum, the lower false positive rate is `false_positive / reviewed`; the upper rate adds `unclear` to the numerator. The destination strata include `fresh_dust_funded`, `implicit` and `other`.

A live window can be restarted at the latest finalized block only after the entire previous state directory is archived. The new state starts with empty counters, fresh-account context, pending keys and transfer cursors; optional coverage_reset metadata records previous_last_height and the restart reason. Feed statistics and the public feed page disclose the precise intervening heights not scanned by the follower once the new start height is known. They retain a notice that up to 10 minutes of prior key/outflow context and 24 hours of fresh-account context are missing at the window start. Transfers API windows are separate and can include earlier data; the gap is not a claim that every signal missed every height.
