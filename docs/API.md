# API

This file is the consumer contract of the verdict interface: what `gate.verdict.request` returns, which checks can appear in it and what each status means, how `outcome` and `action` relate, a recorded answer for ALLOW and for DENY, and the local HTTP endpoint that serves it.

`tests/test_api_doc.py` checks the response field names and order, exact check ids, `Kind` rows against emitted near/ft check ids, and `Tier` rows against `TIER2_CHECKS` plus allowlisted and off-allowlist ft calls. It checks that `issuer_blacklist` appears only when an issuer table is passed and `community_report` only when `reports_account` is set; for CLI, MCP and HTTP it verifies `issuers_for("mainnet")` for Gate ids not ending `.testnet` and no issuer table for `.testnet`; and it checks the outcome/action rows: ALLOW is `ask` when `ask` is nonempty and otherwise `sign`, DENY is `refuse`, and UNKNOWN is `ask`. It also checks the ALLOW and DENY examples against their fixtures with 64-hex values shortened, and that the committed UNKNOWN fixtures are exactly the top receiver judgements whose verdict is UNKNOWN while the UNKNOWN example section cites no fixture. The meanings in the `pass`, `signal` and `unknown` check-table cells are documentation checked by review, not by a test.

## The verdict response

`gate.verdict.request` (`gate/verdict.py:61`) judges one transfer and returns a dict with exactly these keys, in this order (`gate/verdict.py:134-146`). Every adapter (the CLI `python -m gate verdict`, the MCP tool `check_near_payment`, the HTTP endpoint, the pay wrapper) starts from this dict.

### Fields

| Field | Type | Meaning | Code |
|---|---|---|---|
| `outcome` | string | `ALLOW`, `DENY` or `UNKNOWN`, the verdict of `gate.rules.judge` | `gate/verdict.py:135`, `gate/rules.py:868` |
| `action` | string | `sign`, `ask` or `refuse`: what the caller does with the outcome (see Outcome and action) | `gate/verdict.py:136`, `gate/verdict.py:104-105` |
| `ask` | list of strings | the reasons a human must decide before anything is signed or sent; empty for DENY | `gate/verdict.py:137`, `gate/verdict.py:20-58` |
| `verdict` | object or null | the Verdict object the Gate's `request_transfer` takes: `literal`, `issued_ms`, `expires_ms`, `verdict_id`, `evidence_hash`, `key_id`, `signature`; null unless the outcome is ALLOW and the action is in the caller's `sign_actions` | `gate/verdict.py:138`, `gate/verdict.py:106-109`, `gate/verdict.py:120-133` |
| `request` | object | the TransferRequest judged: `kind`, `token_id`, `receiver_id`, `amount` (the canonical decimal string), `memo` (string or null) | `gate/verdict.py:139`, `gate/verdict.py:96-98` |
| `checks` | list of objects | one object per check that ran, `{id, status, detail, source}`, in the order the rules ran them (see Checks) | `gate/verdict.py:140`, `gate/evidence.py:43` |
| `reasons` | list of strings | the reasons for the outcome | `gate/verdict.py:141`, `gate/rules.py:810-844` |
| `evidence_hash` | string | the sha256 hex of the canonical bytes of the evidence document, which is also its file name | `gate/verdict.py:142`, `gate/verdict.py:117-118` |
| `evidence_path` | string | where the evidence document was written, `<evidence_dir>/<evidence_hash>.json` | `gate/verdict.py:143`, `gate/evidence.py:93-100` |
| `latency_ms` | integer | whole milliseconds from just before the rules run until immediately after the conditional `verdict_id` assignment, following the action and signing decision. An id is drawn only for ALLOW when its action is in `sign_actions`; DENY, UNKNOWN and unsigned ALLOW get no id. The interval excludes request validation before it and evidence-document construction, evidence write and signature afterward. | `gate/verdict.py:144`, `gate/verdict.py:99-110` |
| `message` | string or null | the canonical message the signature covers (`docs/VERDICT-RECORD.md`), or null when `verdict` is null | `gate/verdict.py:145`, `gate/verdict.py:120-124` |

The adapters change the dict in two places only. The HTTP endpoint drops `evidence_path`, sets `verdict` and `message` to null and adds `signing` (`gate/http.py:163-164`). The MCP tool adds `gate`, `signer`, `agent_pk` and `policy_source` (`mcp/server.py:185`).

### Checks

Each check is `{"id", "status", "detail", "source"}` (`gate/evidence.py:43-47`). `status` is `pass`, `signal` or `unknown` (`gate/evidence.py:27`); `evidence.check` raises on any other value, and there is no `not_run` status: a check that did not run is absent from `checks`. `detail` is text for a human. `source` is `{"provider", "request_sha256", "fetched_at"}` (`docs/VERDICT-RECORD.md`): the RPC or HTTP host with the replay key of the request and its fetch time, or for a local read a local provider name (`label store`, `local patterns`, `allowlist and label store`, or `nearblocks` when no request was made) with `fetched_at` null (`gate/rules.py:117-122`).

Tiers (`gate/rules.py:857-865`): tier 1 runs for every receiver; tier 2 runs only for a receiver that is not on the agent's `allowlist` in the policy (`TIER2_CHECKS`, `gate/rules.py:37`). Kind `near` runs no token check; kind `ft` adds the three token checks and also looks the token up in the label store (`gate/rules.py:427-432`, `gate/rules.py:441-461`).

With an archival client and a readable receiver, tier 2 reads `view_access_key_list` first, then dates its oldest usable nonce with archival `block_at`; when there is no usable nonce, it reads the archival block and then `view_account` in sequence. An archival pass is final, and the archival path never signals. If archival age is unknown, `account_age` falls back to NearBlocks account keys; when the oldest listed key is younger than 7 days it reads that key's transaction to see whether it created the account, and `dust_funded` reuses that read. An implicit account created by a plain transfer is never proven created, so when its oldest listed key is younger than 7 days its age reads unknown, never a signal. When the oldest listed key is older, `dust_funded` requests that transaction only when the keys response includes its hash, and reads its deposit only when the same test shows it created the account. On either path, when account age passes and nothing is a lookalike, `dust_funded` passes without a deposit it did not or could not read, since a deposit is a signal only with a lookalike or a young account. On the default path, `dust_funded` stays unknown without a NearBlocks request when a lookalike is found; a resulting DENY keeps its deciding lookalike reason but loses the sentence naming a 0.01 NEAR creation deposit. These are the only tier 2 checks that request NearBlocks on the fallback path. Any check that cannot run remains `unknown`, and UNKNOWN is refused.

NearBlocks is a fallback source whose terms are under review. Its free plan is for personal use, and its terms prohibit third party apps from interacting with the service without prior written consent; none was sought or given. The hosted `/live/verdict` route does not read it unless `SIYAB_VERDICT_NEARBLOCKS=1` ([Opt-in live API](#opt-in-live-api)). On testnet, NearBlocks API v1 was retired on 2026-11-05 and returns HTTP 410 with `API v1 was retired on 2026-11-05. Use /v3`; mainnet v1 still answers.

FastNEAR supplies the RPC, archival RPC and transfers reads used here. It publishes no terms of service or rate limits for those interfaces; this dependency is unverified on those two points.

The issuer source records current token blacklist views as `onchain` `denylist` assertions with `python -m intel issuers seed`; `label_denylist` reads them from the store, while `issuer_blacklist` remains a separate view check.

Line numbers without a file are `gate/rules.py`. The test compares the table's check ids with the literal first arguments of `evidence.check` calls in `gate/rules.py`. It does not validate the prose in the `pass`, `signal` and `unknown` columns; those descriptions are checked by review.

### Outcome and action

`outcome` comes from the statuses alone (`gate/rules.py:867-868`): DENY when any check is `signal`, else UNKNOWN when any check is `unknown`, else ALLOW. A signal wins over a check that could not run.

`action` comes from `outcome` and `ask` (`gate/verdict.py:103-105`):

| `outcome` | `ask` | `action` |
|---|---|---|
| `DENY` | always empty (`gate/verdict.py:28-29`) | `refuse` |
| `UNKNOWN` | each check that could not run, as `<id> could not run: <detail>`, then any Gate policy refusal below (`gate/verdict.py:38-40`) | `ask` |
| `ALLOW` | a Gate policy refusal the verdict service can see: the Gate is paused, the agent is disabled, the receiver is on the Gate denylist, or the receiver is off the allowlist with no unknown payee caps, no cap for the asset, or an amount over that cap's per call limit (`gate/verdict.py:32-58`) | `ask` when `ask` is not empty, else `sign` |

`sign_actions` decides only which actions are signed, never the action itself (`gate/verdict.py:61-63`, `gate/verdict.py:104-106`): the default `("sign",)` signs an ALLOW whose action is `sign`; ordinary pay leaves that default in place (`gate/agent.py:208-225`, `gate/agent.py:286-361`), and the HTTP endpoint passes `()` (`gate/http.py:160`). DENY and UNKNOWN are never signed. The Gate itself still checks the window part of every cap, the caps of an allowlisted payee, and the verdict signature, expiry and replay (`contracts/gate/src/lib.rs:194-210,227-237`; `contracts/gate/src/verdict.rs:66-95`).

Adapters translate `action` into their host's vocabulary (pay or not, a tool result, an HTTP body) and never decide again: `mcp/server.py:182`, `gate/http.py:163-164` and `gate/agent.py:311` read `result["action"]` as it came back.

### UNKNOWN

The committed UNKNOWN verdicts are exactly the top receiver judgements whose verdict is UNKNOWN, under `fixtures/receivers/top/judgements/`; they reflect incomplete data for real mainnet receivers. The 84 receiver judgements under `fixtures/receivers/judgements/` record no UNKNOWN. The example was `fixtures/receivers/judgements/liver.pool.near.json`, a mainnet staking pool of the recorded receiver set that read UNKNOWN on `account_age` and `dust_funded`, until the archival `view_account` read dated the receivers with no access key (`docs/SPIKES.md` S8); it now records ALLOW. The incident page `intel/incidents/rhea.json` also contains UNKNOWN `rules_today` entries, judged without the archival client; these are not separate fixture records. An UNKNOWN answer has the fields of The verdict response with `"outcome": "UNKNOWN"`, `"action": "ask"`, an `ask` that names each check that could not run as `<id> could not run: <detail>` (Outcome and action), and `verdict` and `message` null. `tests/test_api_doc.py` checks that committed UNKNOWN fixtures are exactly those top receiver judgements and that this section cites no fixture.

`python -m gate demo --offline` prints an answer of each outcome, an UNKNOWN among them, over the recorded testnet fixtures in `fixtures/demo/`. Its evidence goes to a temporary directory, and its latency, and so its evidence hash, changes from run to run, so it is not cited here.

## The verdict endpoint

`python -m gate http` serves `gate.verdict.request` over HTTP from `gate/http.py`, on the Python standard library server. It is local: it binds `127.0.0.1` by default (`--host`, `--port`, default port 8788) and speaks plain HTTP. It is not hosted anywhere and it is not paid. TLS is the job of a reverse proxy in front of it; the process itself has no certificate.

### The unsigned rule

The endpoint never signs. It reads no signing key, builds no verdict signer and calls `gate.verdict.request` with `signer=None` and `sign_actions=()`, so no outcome, not even an ALLOW whose action is `sign`, carries a Verdict object. Every answer has `verdict` and `message` null and the field `signing` with the text "this endpoint does not sign; a signed verdict needs the verifier key, which is never on this server". A Gate pays only on a signed ALLOW, so an answer from this endpoint alone pays nothing: a verdict a Gate pays on still comes from the operator's verdict service holding the live key (README, Integrate).

### Keys and rate

`SHIELDBOT_API_KEYS_FILE` names a file of API keys, one per line; blank lines and lines starting with `#` are skipped, and each line is stripped of surrounding whitespace. Without that variable, with a file that cannot be read or with a file that holds no key, the server prints `not started: ` and the reason and exits 2: there is no open mode. A caller sends `Authorization: Bearer <key>`; SHA-256 digests of the presented key and every key in the file are compared with `hmac.compare_digest`.

Each key gets `SHIELDBOT_API_RATE` requests a minute (default 60, at least 1), counted in the process in fixed 60 second windows; the count starts again when the process restarts. A request past the budget is answered 429 with `Retry-After` in whole seconds until the next window. Each connection has a 10 second socket timeout. At most eight requests are in flight; excess requests are answered 503 without reading their bodies. `GET /health` needs no key and is not counted.

### Mode

By default the endpoint judges over the recorded fixtures (`GATE_FIXTURES_MODE` unset or `replay`), the way the MCP server's `check_near_payment` does offline: bound to `GATE_ACCOUNT_ID` (default `gate.near`) and the TEST agent key, against `GATE_POLICY` (JSON in the `get_agent` shape; default the MCP server's `DEFAULT_POLICY`, no allowlist and no caps). Live reads need `GATE_FIXTURES_MODE=off` and a `GATE_ACCOUNT_ID` ending `.testnet`; they are still unsigned. `GATE_FIXTURES_MODE=record`, or `off` with any other Gate, refuses to start. There is no mainnet live path. `REPORTS_ACCOUNT_ID`, read at startup, enables the `community_report` check against that contract; when unset, the check is omitted. Evidence documents go to a temporary directory the server names on start, removed when it stops unless `GATE_KEEP_EVIDENCE=1`.

### POST /verdict

The request body is one JSON object of at most 65536 bytes with the fields `check_near_payment` takes, and no others:

| Field | Value |
|---|---|
| `kind` | `near` or `ft` |
| `token` | the NEP-141 token account, for kind `ft` |
| `receiver` | the receiving NEAR account id |
| `amount` | the amount in base units, as a decimal string |
| `memo` | the transfer memo, or absent |

```
curl -s http://127.0.0.1:8788/verdict -H "Authorization: Bearer $KEY" \
  -d '{"kind": "ft", "token": "wrap.near", "receiver": "intents.near", "amount": "1000", "memo": "invoice 7"}'
```

The answer is the `gate.verdict.request` result described in The verdict response, with three changes (`gate/http.py:163-164`): `evidence_path` is removed, `verdict` and `message` are always null, and `signing` is added with the unsigned rule above. `action` is passed through unchanged, so an ALLOW whose action is `sign` still says `sign` although nothing was signed. The default Gate `gate.near` does not end `.testnet`, so the endpoint runs `issuer_blacklist` (`gate/http.py:150`, `gate/rules.py:404`, `gate/rules.py:800`); with `intents.near` allowlisted and a `wrap.near` cap in `GATE_POLICY`, the body above answers ALLOW with the seven tier 1 checks `receiver_exists`, `label_denylist`, `issuer_blacklist`, `token_in_catalog`, `ft_metadata_sane`, `storage_registered` and `memo_injection`. The recorded examples are under Examples.

### GET /health

`{"ok": true, "mode": "replay"}`, or `"mode": "live"` with live reads; no key needed.

### Errors

Every answer is JSON with `Cache-Control: no-store`; an error is `{"error": "<text>"}`.

| Status | When |
|---|---|
| 400 | the body is not JSON, not an object, has a field other than the five, or holds a transfer `gate/canon.py` refuses (`invalid request: ` and the `CanonError` text); a `Content-Length` that is not a byte count or is longer than 10 digits |
| 401 | no `Authorization: Bearer` header, or a key not in the file (with `WWW-Authenticate: Bearer`) |
| 404 | `GET` or `POST` to any path but `/verdict` and `/health` |
| 405 | any method other than `GET` and `POST` (with `Allow: GET, POST`), or `GET`/`POST` on a known path that does not accept it (with the route's `Allow`) |
| 411 | no `Content-Length` |
| 413 | a `Content-Length` over 65536, answered before the body is read |
| 429 | the key is past its budget for the minute (with `Retry-After`) |
| 500 | the verdict failed for another reason; the body is `{"error": "internal error"}`, and the exception type and text go to stderr, never a traceback in the body |
| 503 | all eight request slots are occupied; the request body is not read |

Unsupported methods are rejected before path, in-flight capacity and key checks. Supported requests then hit the in-flight cap, path, route method and, for `POST /verdict`, key, budget, `Content-Length` and body. The tests are in `tests/test_http.py`.

## The quote preflight

`gate.intents.judge_quote`, the CLI `python -m gate intents` and the MCP tool `check_intents_quote` judge where a NEAR Intents 1Click quote sends money on an EVM chain. The MCP answer has the keys `verdict`, `checks`, `reasons`, `quote`, `document`, `evidence_hash` and `deposit_address_check`. It is unsigned on every outcome.

- Dry only. The request body always carries `"dry": true`, and `dry_quote` raises before any request for another value. A well formed answer that echoes `dry: true` passes `quote_dry`, whether or not it contains `depositAddress`. The answer is held to the quote answer schema for every field the leg reads (`_answer_schema`): `quote` and `quoteRequest` must be objects, `amountOut` and `minAmountOut` in `quote` decimal strings without sign, spaces or leading zeros (`0` is one), the schema's string amount, and `correlationId` and `timestamp` strings. The schema requires all four, so an absent or null one, a `minAmountOut` of null included, makes `quote_dry` unknown, and so does an amount such as `-1`, ` 5`, `1.5` or `0x10`; a `timestamp` string that is not a complete date-time with an explicit zone makes `quote_age` unknown instead. 1Click documents that a dry quote is simulated without generating a deposit address. Nothing can be deposited from that dry quote.
- Request schema. One validator, `_request_schema`, holds every quote request to the recorded quote request schema (`intel/seeds/raw/intents-quote-doc-20261029T114539Z.md`). Its twelve required fields (`dry`, `swapType`, `slippageTolerance`, `originAsset`, `depositType`, `destinationAsset`, `amount`, `refundTo`, `refundType`, `recipient`, `recipientType`, `deadline`) must be present, and a schema field that is present, null included, must have the schema's type: `dry` and `insured` booleans; `slippageTolerance` and `quoteWaitingTimeMs` numbers, an integer or a finite float and never a boolean; `swapType`, `depositType`, `refundType`, `recipientType`, `depositMode` and `confidentiality` one of their enum values; `amount` an integer string without sign, spaces or leading zeros; `deadline` a complete date-time with an explicit zone (see below); `originAsset`, `destinationAsset`, `refundTo`, `recipient`, `sessionId`, `virtualChainRecipient`, `virtualChainRefundRecipient`, `customRecipientMsg` and `referral` strings; `connectedWallets` a list of strings; `appFees` a list of `{recipient, fee}` objects with a string recipient and a number fee; and `rebates` a list of `{recipient, share}` objects with a string recipient and a number share from 0 to 100. A key outside the schema is left to the key lists below. The validator runs in four places. On the request built from the caller's arguments it runs before any request, so a value outside it is an `invalid request`: an `origin_asset` of false, 0, a list, an object or null, or a `recipient_type` outside its enum, an empty string included. On the dry echo it runs after the comparison with the sent request: a sent field echoed differently is a signal, as below, and any other value outside the schema makes `quote_dry` unknown, such as `connectedWallets` false, `sessionId` an object, `quoteWaitingTimeMs` `"banana"`, `virtualChainRecipient` a list or a null informational key. On the caller's later request it runs in `verify_binding` after the comparisons, and a value outside it is refused by name. On the status quote request it runs after the status comparisons, and a value outside it makes `deposit_address_status` UNKNOWN. The informational keys and the empty values the key lists allow (an empty string or list for the virtual chain, custom message and rebate fields) pass only with the schema's type.
- Verdict binding. The judged request carries the refund account and refund type the caller names (`refund_to`, `refund_type`, `--refund-to`, `--refund-type`; by default `intents.near` and `ORIGIN_CHAIN`, only when the argument is left out: a supplied value that is not a non empty string, an MCP null included, is an `invalid request`, and so is a `refund_type` other than the schema's `ORIGIN_CHAIN`, `INTENTS` or `CONFIDENTIAL_INTENTS`, `origin_chain` included, except that with `deposit_address` a missing or null `refund_to` is refused as required, and a supplied MCP `recipient_type` or `--recipient-type` must be one of the schema's `DESTINATION_CHAIN`, `INTENTS` or `CONFIDENTIAL_INTENTS`, or it is an `invalid request`; `INTENTS` and `CONFIDENTIAL_INTENTS` are judged and read UNKNOWN on `destination_supported`) and `appFees` only when the caller names app fees. The answer's `quoteRequest` must echo every field sent, or `quote_dry` is a signal and the verdict is DENY; the deadline is compared as the same instant, because 1Click echoes it with milliseconds added. Its `appFees` must be exactly the named app fees, or those plus the service fee `fixtures/oneclick/service-fee.json` records: the one fee, 20 basis points to one implicit account, that 1Click added by itself to the recorded dry echo of a request that named none (`fixtures/intents/d765b63a...json`). The leg reads that file each time it judges a quote; for a file it cannot read, see Missing data below. Any other fee, an `appFees` that is not a list, a key outside the judged request and the status key lists below, a `depositMode`, `insured` or `confidentiality` other than the default, and a set `virtualChainRecipient`, `virtualChainRefundRecipient`, `customRecipientMsg` or `rebates` are a signal too, each named in the `quote_dry` detail; a passing detail says whether the echo added the service fee. `verify_binding` checks the evidence hash, kind and verdict, refuses a document whose subject has no `quote_request` (one written before request binding) with that reason whatever its verdict, and requires `BOUND_FIELDS` (`originAsset`, `destinationAsset`, `amount`, `recipient`, `recipientType`) and `REFUND_FIELDS` (`refundTo`, `refundType`) in the caller's request, equal to the judged ones, and then `_request_binding` with the deadline: every judged field but `dry` must be present (`swapType`, `depositType`, `slippageTolerance` and `deadline` included) and equal, the deadline as the same instant, so a missing, malformed or different deadline is refused, `appFees` must equal the app fees the caller named (none when none were named, and an absent `appFees` means none), `slippageTolerance` must be a number no higher than the judged one (a judged `slippageTolerance` that is not a number is refused), the default and empty keys must hold, and a key outside these is refused by name, and then the request schema above holds; `dry` is not compared, because a later real quote is not dry. The amount the caller names (`amount`, `--amount`) must be a decimal string from 1 to 2**128 - 1 without sign, spaces or leading zeros, the schema's integer string and the rule `/live/intents` applies, so `0`, `-5`, ` 1`, `1e6`, a JSON number, a boolean or a list is an `invalid request` before any request; `verify_binding` refuses, by name, a judged amount or refund type outside these rules, and compares every other field with equal types, so a boolean never equals a number. The CLI and MCP tool verify the request built from the same arguments they judged, the named app fees included. The service fee binds only in the dry echo: a later request or status quote request must carry the named fees and no other. `verify_binding` reads its clock once for an ALLOW and refuses it when the judged deadline is not after that reading or when the quote timestamp in the document is missing, invalid or more than 300000 ms old at it, so an ALLOW ends at its quote deadline and when its quote ages past the bound; an intact UNKNOWN or DENY answer that passes these checks is not refused, whatever the clock, and the MCP tool returns it with its checks and evidence hash. The quote timestamp has a separate age bound of 300000 ms; a missing, invalid, future or older timestamp makes `quote_age` UNKNOWN. Its age is taken at the same clock as `quote_deadline` below, so a quote that ages past the bound during the later reads is UNKNOWN too. The judged deadline has its own check, `quote_deadline`: a deadline that is not after the judge's clock makes it UNKNOWN, so such a quote is never ALLOW; that clock is read once after the last external read (the quote, GoPlus, `eth_getCode` and the firewall) and is the document's observed time, so a deadline that passes during those reads is UNKNOWN too. Every deadline and the quote timestamp must be a complete date-time with an explicit zone, the request schema's `date-time` format (`2026-11-03T12:10:00Z`, `2026-11-03T12:10:00.000Z` or `2026-11-03T13:10:00+01:00`); a date alone, a time without a zone, another ISO form or a component out of range (month 01 to 12, day 01 to 31, hour 00 to 23, minute and second 00 to 59, offset hours 00 to 23 and minutes 00 to 59, so `+01:60` is never read as `+02:00`) is invalid: `judge_quote` refuses such a deadline by name before any request (the CLI answers `invalid request`, the MCP tool an `invalid request` error), `verify_binding` refuses it by name, and as the quote timestamp, a status deadline or the real quote deadline or timestamp in a status answer it reads UNKNOWN. In replay the CLI and MCP tool send the recorded deadline, 2026-10-30T00:00:00Z, so no replayed quote is ALLOW after that time; the recorded demo is DENY on its theft label either way.
- OFAC sanctions. `ofac_sanctioned` reads the committed local SDN address fixture for the destination recipient and never uses the network. A `0x` plus 40 hex recipient is matched by its normalized EVM key across all listed digital-currency codes, independent of whether the destination chain has a published code. Other recipient formats use only the asset codes mapped to that destination chain; a chain with no mapped code passes with detail that the list publishes no address for that chain. A match is a signal and makes the verdict DENY with the SDN uid, entry name, programs, list date and source XML hash in its reason. A no-match pass records the list date and the number of distinct comparison keys checked. `docs/SANCTIONS.md` lists the mapped codes and explains the EVM rule. A missing or unreadable fixture is UNKNOWN. Its evidence source names the fixture and carries the hash of its JSON bytes.
- The NEAR payment path (`gate/rules.py`) is unchanged: OFAC publishes no NEAR account.
- Theft labels. `recipient_theft_label` passes only when GoPlus `address_security` answers `code` 1 as an integer (true, 1.0 or `"1"` is not the success code) with a non empty `result`, and each theft label present in it is `"0"` or `"1"`, the shape of the recorded answers in `fixtures/goplus/`; a theft label may be absent. Any `"1"` is a signal. Without a `"1"`, a theft label with any other value, null, a number, a boolean or another string, makes the check UNKNOWN, and so does another code.
- Firewall. When the recipient has contract code and `SHIELDBOT_API_URL` is set, `recipient_code` asks the ShieldBot firewall about a native value transfer of the quote's `amountOut`. A classification in `FIREWALL_SIGNALS` (`HIGH_RISK`, `BLOCK_RECOMMENDED`) is a signal, from a complete or a partial scan. Any other classification passes only on a complete scan: `status` exactly `ok`, `partial` exactly false and `failed_sources` exactly an empty list, and the classification one of the `non_signals` listed in `fixtures/firewall/classifications.json`. Anything else is UNKNOWN: another status, a missing or non false `partial`, a `failed_sources` that is missing, null, false, 0, an empty string, an object or a non empty list, a classification the list does not name, a quote with no `amountOut`, or a firewall that cannot be reached; for a list file it cannot read, see Missing data below. Without contract code the firewall is not called; with code and no `SHIELDBOT_API_URL` the check is UNKNOWN. A firewall pass is never named in an ALLOW reason.
- Deposit address. A dry quote has no deposit address. Only when the caller supplies the address from a real quote with `--deposit-address` or MCP `deposit_address`, the CLI or MCP tool makes a read only `GET /v0/status?depositAddress=<address>` on the same 1Click base URL. The caller must name the real quote's refund account with it, or the call is refused. The status answer's `quoteResponse.quoteRequest` is compared by `_status_binding`: `dry` must be `false`, since a deposit address comes only from a real quote, and every judged field but `dry`, `deadline` and `slippageTolerance` must be equal (`refundTo`, `refundType`, `swapType` and `depositType` included), `appFees` must equal the app fees the caller named (none when none were named), `slippageTolerance` must be a number no higher than the judged one, `depositMode`, `insured` and `confidentiality` must be absent or `SIMPLE`, false and `public`, `virtualChainRecipient`, `virtualChainRefundRecipient`, `customRecipientMsg` and `rebates` must be absent or empty, and any key outside these and `connectedWallets`, `sessionId`, `referral` and `quoteWaitingTimeMs` is refused. A differing field is refused by name. A status quote request the request schema above does not allow, a missing or malformed deadline included, makes `deposit_address_status` UNKNOWN. The real quote the status answer carries is held to its own time fields too, at the places the recorded quote answer schema puts them: `quoteResponse.quote.deadline`, the time the schema says the deposit address becomes inactive, and `quoteResponse.timestamp`. A `quoteResponse.quote` that is not an object, or a real quote deadline or timestamp that is missing, null or not a complete date-time with an explicit zone (see below), makes `deposit_address_status` UNKNOWN. The real quote must also carry `quoteResponse.quote.depositAddress`, a string in the recorded quote answer schema, exactly equal to the supplied address (no trimming or case folding): a missing, null, non string or different value makes `deposit_address_status` UNKNOWN. The status answer's own status is read from its top level `status` key and must be a string in `DEPOSIT_STATUSES`. The recorded documentation covers the quote endpoint only, so neither that key nor the status endpoint's values are recorded, and `DEPOSIT_STATUSES` is empty: a missing, null or non string status and every string status, `PENDING_DEPOSIT`, `REFUNDED` and `SUCCESS` included, make `deposit_address_status` UNKNOWN. A supplied deposit address therefore never leaves an ALLOW until the status endpoint's values are recorded; the checks before it still run in order, and the first one that fails names its own reason. The clock is read once after the status read, the last external read of this path, and that one reading judges the status deadline, the real quote deadline, the real quote age, the judged deadline and the judged quote age: a status deadline, real quote deadline or judged deadline not after it, or a real or judged quote timestamp in the future or more than 300000 ms old at it, makes `deposit_address_status` UNKNOWN, so a bound that passes during the status read never leaves an ALLOW, and neither does a real quote that is already inactive or older than the bound when its address is supplied. A 404 means 1Click does not know the address and is refused. A failed read, including a network error, 401 or 5xx, makes `deposit_address_status` UNKNOWN with its reason. An UNKNOWN status check turns an ALLOW answer into UNKNOWN and leaves a DENY answer DENY. No live status answer is recorded, so a real quote that carries an app fee 1Click adds on its own is refused unless the caller names that fee too, and the real quote's time fields and deposit address are read where the recorded schema puts them; no status value is accepted, so no live status answer binds yet. No other endpoint is called, and nothing is signed, deposited or submitted.
- Without a supplied address, the CLI says the address was not checked because dry quotes have no deposit address. The MCP answer's `deposit_address_check` says the same. With an address, the result records the status lookup check in its evidence.
- Signature. The recorded 1Click answer has a `signature` field. It is not verified: no 1Click verifying key is recorded in this repository, and the committed fixture replaces the signature with a note (`tests/test_intents.py:1-3`).
- Replay. Quote and status requests use `gate.rpc.Client` and the `replay`, `record` and `off` fixture modes. Status GET parameters are part of the fixture key, and replay reads a matching recorded response from `fixtures/intents/`. The status answers in the tests are synthetic and marked `synthetic: true`; no live status answer is committed. The tests are in `tests/test_intents.py` and `tests/test_rpc.py`.
- Missing data. The leg reads two local data files each time it judges a quote: `fixtures/oneclick/service-fee.json`, the 1Click service fee, and `fixtures/firewall/classifications.json`, the firewall's `non_signals`. Missing local data never accuses a recipient and never passes one. When `service-fee.json` is missing, unreadable or holds anything but a `{recipient, fee}` with a whole fee, an echo that adds exactly one unnamed app fee, a `{recipient, fee}` with a whole fee, to the named ones makes `quote_dry` unknown and the verdict UNKNOWN, never ALLOW, with the fee and the read failure in its detail; an echo with exactly the named fees still passes, and any other `appFees` difference or other echo difference is still a signal. - Unencodable text. A 1Click dry quote, 1Click status, GoPlus or firewall answer holding a lone surrogate anywhere (valid JSON such as `"\ud800"`, text with no UTF-8 form, so no evidence document can record it) makes its check, `quote_dry`, `deposit_address_status`, `recipient_theft_label` or `recipient_code`, UNKNOWN with the detail `holds a lone surrogate, text with no UTF-8 form`, even when the same answer carries a signal. - Deep nesting. A 1Click dry quote, 1Click status, GoPlus, `eth_getCode` or firewall answer nested too deeply to parse makes its check UNKNOWN with the detail `MalformedResponse: the body is nested too deeply to parse`, and an `--app-fees` value nested too deeply to read is an `invalid request` with exit code 2.

## Workspace accounts and watches

`intel/workspace_api.py:WorkspaceAPI` serves `/workspace-api/` separately from public live reads. `GET /workspace-api/session` includes `registration_open` as a boolean in authenticated and anonymous replies. Successful registration, login and recovery replies include it too (`WorkspaceAPI.handle`, `WorkspaceAPI._auth_reply`). `SIYAB_REGISTRATION=open|closed` is read at API construction, defaults to `open`, and rejects any other value at startup (`WorkspaceAPI.__init__`). `POST /workspace-api/auth/register` without an access code with registration closed answers 403 `{error: "registration_closed", message}` and creates no account, team or session. The closed message invites users to enter an access code if given one. Login and recovery remain available (`WorkspaceAPI._auth`).

`POST /workspace-api/auth/register` accepts `username`, `password` and an optional string `access_code`. A valid code bypasses public registration closure, global sign-up caps and the registration address counters, consumes one use atomically and reserves the user. An invalid, expired or exhausted code answers 403 `invalid_access_code` with "The access code is not valid or has no uses left." A taken username consumes no use. Reserved users are excluded from the public global window counts. Public defaults are 20 per UTC hour and 100 per UTC calendar day, preserved across restarts. `SIYAB_REGISTRATIONS_PER_HOUR` accepts 1 to 200; `SIYAB_REGISTRATIONS_PER_DAY` accepts 1 to 2000 and must be at least the hourly setting. Both are validated when the store starts. The next public account past either cap answers 429 `registration_limit` without creating anything, inviting code holders to the Access code field. `Retry-After` is the whole seconds until every full global window has turned. Public registration attempts also have per-address caps of 5 per hour and 10 per day. These counters live in process memory, use fixed windows beginning with the first counted request, and reset when the API restarts. Their 429 `rate_limited` reply gives the exact seconds remaining in that window. The 120 workspace requests per minute, 10 authentication requests per minute and identity limits apply even with a code; recovery retains its 5-per-hour address cap.

`python -m intel workspace-access-code --state-dir <state> --uses 20 --days 30` prints a newly minted code once and its expiry. Uses range from 1 to 50, days from 1 to 60, with at most 100 remaining unexpired uses across all codes. `--list` prints only creation, expiry and uses left; `--revoke` zeroes all uses; `--grant <username>` reserves a known user. The command requires an existing workspace database outside the repository. Codes are stored only as hashes (`SQLiteWorkspaceStore.create_access_code`, `list_access_codes`, `revoke_access_codes`, `grant_reserved`).

Workspace client buckets use the rightmost comma-separated entry of the last `X-Forwarded-For` header line only when the socket peer is `127.0.0.1` or `::1`. A malformed selected address answers 400 `invalid_request`. Other peers ignore the header. IPv4-mapped IPv6 clients use their IPv4 bucket. IPv4 clients are keyed per address; IPv6 clients in the same /64 share request and authentication buckets (`intel/workspace_api.py:WorkspaceAPI.handle`).

New team creates and joins are limited to 3 memberships per user, including the initial workspace, and answer 409 `team_limit` with "An account can belong to at most 3 teams." Existing memberships above the cap are retained (`intel/workspace.py:MAX_TEAMS`, `SQLiteWorkspaceStore.create_team`, `SQLiteWorkspaceStore.join_team`).

Watch additions and imports retain the 100-account team bound and permit 5 distinct active accounts per adding user across teams. Only that creator is charged; the same account they add in several teams costs one user slot, and leaving a team does not release its active watch. Duplicate team watches preserve attribution. Old active watches are attributed from their latest `watch.added` audit entry when present; unattributed watches count only toward team and public pool limits. Distinct accounts use separate public and reserved pools, default 90 and 30. `SIYAB_WATCH_PUBLIC_ACCOUNTS` accepts 0 to 500 and `SIYAB_WATCH_RESERVED_ACCOUNTS` accepts 0 to 100, validated at store startup. A reserved creator moves an account into the reserved pool even if public users also watch it. Removing its last reserved watch returns it to public, which can temporarily exceed its cap; caps apply only on add and never delete existing watches. A public user adding an already watched account costs no new pool slot. Full pools answer 409 `watch_limit`: "The reserved watch pool is full." or "The public watch pool is full. Accounts created with an access code use a reserved pool." Imports check all watches before changing any records. One stderr alert per process fires at public capacity times 4 // 5, 72 of 90 by default (`SQLiteWorkspaceStore._watch_capacity`, `SQLiteWorkspaceStore._watch_alert`). A public watch pool of 0 never raises this alert.

Ordinary-transfer polling claims at most one watched account per 30,000 ms, at most 120 polls per hour and 2,880 provider calls per day. Every poll reads one page of up to 100 transfers within the 20-second provider deadline; a successful account waits at least 60,000 ms. Claimed ticks repeat three lanes: reserved on slots 0 and 2, fresh public on slot 1, rest on slot 3. Fresh means added in the last 900,000 ms. Fallback order is reserved/fresh/rest on slots 0 and 2, fresh/reserved/rest on slot 1, and rest/reserved/fresh on slot 3. Only claims advance the slot. Reserved rows prefer uninitialized then fresh watches; idle shares flow to other lanes, and public churn cannot take reserved shares. With default pools and healthy workers/providers, a single reserved baseline arrives within 65 seconds under any load, all 30 reserved watches can take up to 30 minutes, and a flooded fresh public lane up to 3 hours. Retries and provider failures can take longer. The baseline alerts on newly inserted transfers timestamped at or after the watch's `created_ms` (`added_ms` in polling state), converting milliseconds to nanoseconds, and seeds older transfers without events. Those alerts route to the team inbox. A watch row still uninitialized when this release first opens the database seeds its first page without raising alerts. An initialized poll whose anchor is absent from its single page records a coverage gap. Bounded reads and missing alerts never establish complete history or a favorable verdict (`AccountHistory.poll_watches`).

## Opt-in live API

`python -m intel serve --live` mounts the keyless routes in `intel/live.py`; without `--live`, `/live/...` answers 404 and the hosted JSON API keeps its no-network behavior (`intel/api.py:make_server`, `intel/__main__.py:main`). The live routes never build a signer or read a signing key. The verdict, scan, Intents and Reports routes write nothing to disk; with `--state-dir`, account routes retain public observations in `history.sqlite3` and `portfolio.sqlite3`, and the entity directory uses `entity-sources.sqlite3`, all under that external directory (`intel/api.py:serve`). Retention and worker state are described below and in [Workspaces](WORKSPACES.md#public-data-and-source-bounds). Reads use `gate.rules.judge`, `gate.scan.scan`, `gate.intents.judge_quote`, and the read-only Reports views (`intel/live.py:LiveAPI`, `gate/rpc.py:request_deadline`).

Routes 1 to 3 read mainnet. A `.testnet` NEAR account is refused for the verdict and scan routes. The Intents destination is a 1Click asset id parsed by `gate.intents.parse_destination`; its recipient must be an EVM address. Reports read the testnet contract `reports.kestrelridge-main.testnet` (`intel/live.py:REPORTS_ACCOUNT`, `contracts/reports/src/lib.rs:subject_summary`). The report list route returns the subject's newest 20 reports (`intel/live.py:MAX_SUBJECT_REPORTS`) in index order, with `truncated` true when the subject has more. The contract has no count view, so the route reads the first `reports_by_subject` page of 50; when that page is full it finds the end of the index with one-report pages, doubling past the last offset known to hold a report and then halving back, reads the last 20 index entries and reads each of those rows with `get_report` (`intel/live.py:LiveAPI._reports`). The recent route reads the newest 20 report ids from `totals` with `get_report` (`contracts/reports/src/lib.rs:reports_by_subject`, `contracts/reports/src/lib.rs:totals`).

The verdict and Intents responses have these fields: `outcome`, `action`, `reasons`, `checks`, `evidence_hash`, `freshness`, `verdict`, `signing`, and `latency_ms`. Only `/live/verdict` also returns `evidence`: the exact canonical evidence bytes decoded as a UTF-8 string, whose SHA-256 equals `evidence_hash`. Cached answers retain that same string. `/live/intents` has no new field. The displayed payment check answer can be downloaded and checked offline with `python -m gate verify-receipt <file>`; [section 5 of the verification guide](VERIFY.md#5-check-a-payment-check-receipt-from-siyabxyz) gives a committed sample and the limits of this consistency check. `UNKNOWN` maps to `ASK`; checks use `{name, status, detail}`. `freshness` is the existing observed block and timestamp object, or the timestamp object for an Intents quote. `verdict` is always null and `signing` is always `never`; an ALLOW action still says `sign`, which describes the judgement action only (`intel/live.py:LiveAPI._verdict_shape`).

`/live/verdict` accepts `receiver`, `amount`, and `token`; `token` is `near` or an account id. The contract has no memo query field, so this route judges an absent memo. Amounts are canonical positive decimal strings within the NEAR u128 range. `/live/intents` accepts `destination_asset`, `recipient`, and `amount`, but 1Click also requires an origin asset. Since the route contract omits it, the route uses the recorded source asset `nep141:wrap.near` (`intel/live.py:INTENTS_ORIGIN_ASSET`, `tests/test_intents.py:quote_for`).

Live JSON responses use `Cache-Control: no-store` except successful, query-free `/live/account-data/<id>.json` and `/live/portfolio-data/<id>.json` responses whose exact bytes hash to the requested id: those use `Cache-Control: public, max-age=31536000, immutable` (`intel/api.py:make_server`). Errors use no-store and are never cached in the process. The table lists every route and its cache behavior; HEAD follows GET. Each request is bounded to 25 seconds. Errors have `{error, message}`; statuses are 400 for invalid input, 429 with `Retry-After` for a client past its limits, 503 when the slots, the request ceiling or the client table are full, when a provider budget is spent (with `Retry-After`) or when a required view is unreadable, 504 on timeout, and 500 for an unexpected failure (`intel/live.py:LiveAPI.handle`).

`LiveAPI.handle` applies the live limits in this order (constants in `intel/live.py`):

- Client key. The socket peer, except that when the peer is `127.0.0.1` it is the rightmost entry of the last `X-Forwarded-For` header, so a client cannot choose its key through a proxy that appends to the header; an entry that is not an IP address leaves the peer. An IPv6 address is keyed by its /64, an IPv4-mapped IPv6 address by its IPv4 address, and an IPv4 address by itself (`intel/live.py:LiveAPI._client_ip`).
- Rate and cost, before any slot is taken. Per client and fixed minute: 60 requests (`RATE_PER_MINUTE`) and 240 cost units (`COST_PER_MINUTE`); past either, 429 `rate_limited` with `Retry-After` until the minute turns. Every admitted request is charged; a live cache hit costs 1 unit. The cache is checked under the lock before the cost check without copying its body. Uncached weights (`ROUTE_COSTS`, `intel/live.py:LiveAPI._cost`): portfolio 6 plus the requested `max_tokens` (40 when absent, at most `intel/portfolio.py:MAX_TOKENS`), portfolio-at-block 2 plus 2 per contract, holdings 1 plus `limit` (20 when absent), verdict 10, reports by subject 22 (summary, first index page and 20 reports), reports/recent 21, graph 6, identity 4, intents 4, scan and backfill 2, profile, transactions and transfers 1, and every other route 1. All clients together get 600 requests a minute (`GLOBAL_PER_MINUTE`); past it, 503 `busy`. The client table holds 4,096 clients (`MAX_RATE_CLIENTS`); a new client first drops the entries of earlier minutes, and when the table is still full it gets 503 `busy`, so no client's count is ever evicted.
- Cache. A cached answer is returned here, without a slot.
- In flight. Each client can run 4 upstream reads (`MAX_CLIENT_IN_FLIGHT`), including at most 2 heavy reads (`MAX_CLIENT_HEAVY`), and have 12 requests running, waiting or following (`MAX_CLIENT_ADMITTED`); a 13th gets 429 `too_many_in_flight` with `Retry-After: 1`. A request waits up to 5 seconds from arrival (`QUEUE_WAIT_S`) for its client turn and an upstream slot, rechecking cache and running requests after each wake; a turn wait that expires gets the same 429. Identical requests follow the running read without a turn or a slot, within the 25-second deadline counted from arrival. The reader takes one of 8 slots (`MAX_IN_FLIGHT`), and portfolio, portfolio-at-block, holdings, graph and backfill (`HEAVY_ROUTES`) also take one of 3 heavy slots (`HEAVY_SLOTS`), leaving 5 slots for other routes; a slot wait that expires gets 503 `busy` with `Retry-After: 1`. The server admits at most 32 live connections, including waiters. The investigation page automatically retries 429 or 503 at most twice only when `Retry-After` is a whole number from 1 to 5 and the error is neither `rate_limited` nor `provider_budget`; it checks the request is still current after waiting, keeps its original 25-second abort timer, and then exposes the existing message and Retry button.
- Cache keys, for the cache and single flight, are built from normalised values (`intel/live.py:LiveAPI._cache_key`): the decoded account of an account or scan path, the query fields sorted, the Intents `recipient` lower-cased (the route also judges the lower-cased address) and the portfolio-at-block `contracts` sorted. The cache holds 128 answers and 4 MiB. Only a 200 answer with no provider budget refusal is cached, for 60 seconds, except a portfolio-at-block answer whose every selected balance, metadata and price read succeeded and whose archive write was not paused: a block-pinned read never changes, so it is kept with no expiry until the cache evicts it (`intel/live.py:LiveAPI._settled_block`). Snapshots, the entity directory, history, backfill, enrichment and portfolio-history bypass the cache (`UNCACHED_ROUTES`).
- NearBlocks. Unless `SIYAB_VERDICT_NEARBLOCKS` is `1` (`VERDICT_NEARBLOCKS_ENV`), `/live/verdict` passes the rules a NearBlocks stand-in that sends nothing and raises `RateLimited` (`intel/live.py:_NoNearBlocks`): an account age the archival read cannot date reads unknown, which never passes. With the flag set, a NearBlocks fetch inside a request whose 10-second slot is not free raises `RateLimited` instead of sleeping (`gate/rpc.py:Client._respect_nearblocks`), with the same result.

Provider budgets (`intel/budget.py`). Every real provider fetch (`GATE_FIXTURES_MODE=off`; replay and record never touch the budget) is reserved before it is sent, in `gate/rpc.py:Client._exchange`, against durable SQLite counters that the API and the worker units share. The database is the file `SIYAB_PROVIDER_BUDGET_DB` names, else `provider-budget.sqlite3` in the `--state-dir` of `python -m intel serve`, `history-follow` or `investigation-follow` (`intel/budget.py:DATABASE_NAME`). Without either nothing is counted and no request carries the FastNEAR key, so the key is spent only where it is counted; a database that cannot be opened refuses the call. The reservation checks every window the call falls in and counts it in one `BEGIN IMMEDIATE` transaction, so concurrent processes cannot overshoot; a refused call is not counted and not sent, and raises `gate/rpc.py:BudgetExhausted`, a `RateLimited`. A keyed call carries the FastNEAR key to a FastNEAR host (`intel/budget.py:FASTNEAR_CLASSES`). The caller class comes from `gate/rpc.py:caller_class`: live requests are `anonymous`, except the backfill route, `backfill`, which also counts toward `anonymous`; `history-follow` is `watch`, `investigation-follow` is `investigation`, `feed --follow` is `feed`, and anything else is `operator`. `team` has its budget, but no route sets it yet, because the live route cannot verify a workspace session.

| Caller class and provider | Keyed calls a UTC day | An hour | A minute |
|---|---|---|---|
| `anonymous`, mainnet RPC | 2,500 | 420 | 120 |
| `anonymous`, index and Transfers | 2,200 | 370 | 90 |
| `anonymous`, archival RPC | 800 | 130 | 45 |
| `backfill`, index and Transfers (also counted as `anonymous`) | 500 | none | none |
| `team`, every provider | 1,500 | 250 | none |
| `watch`, every provider | 3,000 | 125 | none |
| `investigation`, every provider | 1,500 | 250 | none |
| `feed`, every provider | 0 | 0 | none |
| `operator`, every provider | 1,500 | none | none |

These are `intel/budget.py:KEYED_LIMITS`; a provider a class does not list gets no keyed call. Every keyed call also counts toward the pooled cap of 13,000 keyed calls a UTC day (`intel/budget.py:POOLED_DAILY`), which refuses every caller class, and toward a cumulative count since the database began. Keyless FastNEAR calls spend no credit but share politeness ceilings across every caller class (`intel/budget.py:KEYLESS_LIMITS`): mainnet RPC 20,000 a day and 2,000 an hour, archival RPC 3,000 a day and 300 an hour. Calls to every other provider are counted per caller class, UTC day, hour and minute without a limit. Reaching 50, 80 and 100 percent of the pooled cap (`ALERT_PERCENTS`) and 300,000 cumulative keyed calls (`CUMULATIVE_ALERT`) each records one row in the `alerts` table and writes one stderr line. A 403 or 429 answering a keyed call starts a 15-minute cooldown shared by every unit (`KEY_COOLDOWN_S`, `intel/budget.py:key_failure`), records an alert, and FastNEAR requests go out without the key until it ends. The feed follower never sends the key (`intel/feed.py:follow`).

A live request whose read was refused answers 503 `provider_budget` with `Retry-After`, the seconds until every refusing window turns (the next UTC minute, hour or day), when its route would otherwise fail; a route that still answers 200 reports the refused reads as unknown or unavailable, the verdict as `ASK`, never `ALLOW`. Neither is cached. Public refusal messages expose no database path, counter name or limit; detailed database errors and spent counter limits go only to stderr. Retained archives stay readable.

When the server runs with a state directory, account reads also retain what they read: profile, holdings, transaction and transfer pages go to the history archive, a graph answer gains a `snapshot` reference, and a portfolio answer gains a `snapshot` reference in the portfolio archive (`intel/live.py:LiveAPI._account_read`). A profile, transaction or transfer page whose rows are all retained already, unchanged apart from their `observed_at`, `fetched_at` and `request_sha256` provenance and the block they were read at (a profile's `native.block_height` and `native.block_hash`), adds no page, whichever retained pages hold those rows: it cites the first of those rows' retained pages that holds every row unchanged, and when none does, each row cites the retained page that last stored it. A transaction or transfer page with no rows adds no page when it matches the account's latest retained page of that kind apart from that provenance and its `pagination.limit`. A holdings page is a window of the account's full token inventory, so it adds no page only when the newest retained holdings page with the same `pagination.offset` and `pagination.limit` holds exactly the same tokens, none missing and none added, each retained unchanged apart from that provenance and a holding's `metadata_source.block_height`, and has the same pagination `total` and `next_offset`; it then cites that page. An empty holdings page adds none only when that newest page is empty too and matches it apart from that provenance. A token that has gone from or been added to that window, or a changed inventory `total` or `next_offset`, therefore adds a page, unless the archive is full and the read answers with `archive_paused` as described below. A current portfolio adds no observation when it matches the account's latest current observation apart from its `observed_at`, `effective_at` and `fetched_at` times and the blocks its native balance and token metadata were read at (an asset's `details.block_height` and `details.metadata_source.block_height` or `block_hash`); a historical portfolio adds none when it matches the latest observation with the same effective time apart from its `observed_at` and `fetched_at` times. A transaction or transfer page is a window of the account's history, so only its rows are compared: a page holding a subset of retained rows, or one that differs only in its pagination, `source` or `coverage`, adds no page and cites the retained pages that hold its rows. For a holdings page that holds tokens, its tokens and its pagination `total` and `next_offset` are compared, not its `source` or `coverage`. A profile page is one row, so the whole profile is compared. Any other difference in a row, or in an empty page, adds a new page, unless the archive rejects the row, as it does a transaction or transfer whose timestamp changed. For a portfolio any other difference, including a balance, a price or its timestamp, or the token inventory, adds a new observation. Retained ids and bytes never change, and a reused page or observation holds every row it is cited for. Investigation jobs cite those retained pages for their rows and copy each cited page's `source` and `observed_at`, so one job read can list more than one observation (`intel/history.py:AccountHistory.record_page`, `intel/portfolio.py:PortfolioHistory.save`, `intel/investigation_jobs.py:InvestigationJobs.tick`). A full archive or a reached budget never fails a read that succeeded. Every retained history page and portfolio observation is checked before the history or portfolio archive reuses, cites or returns it: its bytes must hash to its id and be canonical JSON of the expected shape, naming the mainnet network, and each asset of a portfolio observation must hold its `balance_base_units`, `decimals` and `balance`, each null or of its supported type, with `balance` matching the other two. Investigation job results are not covered: a result returns the rows, page ids and observations the job copied into its private jobs database when it read them, without checking them again. A retained history row must be canonical JSON naming its own row id and, for a transaction or transfer, its retained timestamp, and the retained page it cites must hold it byte for byte; that check passes before a row's timestamp can reject a read as changed or position an archive cursor. When an account read is archived, a retained page, row or observation that fails that check is neither reused nor cited: the read is saved as a new page or observation, which later unchanged reads reuse. Only a read whose own id equals that of a retained page or observation that fails the check fails with 503, and the watch monitor and investigation jobs record that failure as a failed attempt and keep running. Input the archive rejects, such as a transaction or transfer whose timestamp changed, fails the read with 400. Archive browsing, and fetching a retained portfolio observation by id, answer 503 when a row, page or observation they would return or cite, or the row an archive cursor names, fails its check. When the archive is full, the public share of it is used up, or the portfolio capture budget is reached, the route still answers 200 with the live result, adds `"archive_paused": true` and leaves out `snapshot`. Only the backfill route, which exists to archive, answers 503 with `{error: "archive_capacity", message, coverage}` and `Retry-After: 60`.

The history and portfolio databases are written only by Siyab, and these checks are defence in depth against damage to a retained record, not a defence against someone who can rewrite a database together with its hashes. They guarantee that a damaged page, row or observation is never reused or cited, that archive browsing which would return or cite it answers 503 instead of serving it, and that a fresh read of the same history rows replaces a damaged history row and its citation. Portfolio observations are never replaced: a damaged one stays retained while later reads are saved as new observations. A damaged history row that no later read covers, and a damaged portfolio observation, keep archive browsing that reaches them for that account and kind at 503 until an operator repairs them.

A graph `snapshot` is served at `GET /live/account-data/<id>.json` as the exact stored bytes, whose SHA-256 is the id. It answers 503 when the stored body is not bytes, does not hash to its id, or is not a canonical JSON object within the archive nesting and size limits. Transfer events that watch polling records for team inboxes are not public. An event id is a hash of public transfer fields, so a public event route would confirm that some team watches an account or its counterparty; `/live/account-events/<id>.json` therefore answers 404 for every id, exactly as any unknown live path does. A signed-in team member opens an event from the team inbox at `GET /workspace-api/teams/<team>/events/<id>`, which needs the workspace session cookie and serves the exact stored bytes, whose SHA-256 is the id, with `Cache-Control: no-store`. When watch polling has removed a delivered event from the history database to stay within the event or byte budget (`docs/WORKSPACES.md`), the route serves the workspace database's copy of that event instead, only when that copy reproduces the exact bytes whose SHA-256 is the id, and otherwise answers 404 exactly as for an unknown id. Without a session it answers 401, to someone outside the team 403, and for an event that team's inbox does not hold 404, each exactly as for an unknown id, so a member of one team cannot read or confirm another team's events. An event the team's inbox holds answers 503 when its stored body is not bytes, does not hash to its id, or is not a canonical JSON object within the archive nesting and size limits (`intel/workspace_api.py:WorkspaceAPI`, `intel/workspace.py:SQLiteWorkspaceStore.team_event`, `intel/history.py:AccountHistory.get_event_bytes`).

When the archive page, row or byte budget cannot take a watched transfer page, watch polling still records its deduplication entries and raises and delivers its alerts, without archiving that page or deleting any archived page or row; the account keeps incomplete coverage, counted in `coverage_gap_accounts` (`intel/history.py:AccountHistory.poll_watches`). A new alert event makes room by removing delivered events oldest first by recording time, never undelivered events; if these removals cannot make room, the transaction removes nothing and the poll retries later. The 16 MiB event share (`intel/history.py:EVENT_ARCHIVE_BYTES`) admits a new event when total retained bodies including it stay within 128 MiB or retained event bodies including it stay within 16 MiB (`intel/history.py:AccountHistory._reserve`). Pages, rows and graphs that add bytes stop when total retained bodies including events would pass 112 MiB. A database from the previous release may already hold more than 112 MiB and up to 128 MiB of pages, rows and graphs; keeping those bodies plus the event share permits up to 144 MiB of retained bodies. Each write connection sets `PRAGMA max_page_count=131072`, allowing a 512 MiB database file at 4 KiB per page, separate from the body budgets and WAL sidecar files (`intel/history.py:AccountHistory._connection`). Watch deduplication keeps at most 1,000 entries per account and 200,000 globally, removing oldest entries first by insertion order at either cap; the workspace transfer identity prevents a removed entry from raising a duplicate alert or inbox row (`intel/history.py:MAX_ACCOUNT_WATCH_SEEN`, `intel/history.py:MAX_WATCH_SEEN`, `intel/workspace.py:SQLiteWorkspaceStore.ingest_event`). A storage error while a watch tick claims or polls a watched account is recorded in `last_error`, and the history service keeps polling after its interval instead of stopping; an error that escapes the tick is logged and retried by the service loop, while `--once` exits with that error (`intel/history.py:AccountHistory.poll_watches`, `intel/history.py:run`). The watched account list is not bound into one SQL statement, so its length is not limited by SQLite's variable limit (`intel/history.py:AccountHistory.poll_watches`).

The backfill route (`/live/accounts/<account>/backfill`) and team investigation jobs have separate global provider page budgets, 12 pages per minute in all. The backfill route is anonymous: it reserves its `max_pages` up front and answers 503 `archive_capacity` with `Retry-After: 60` when that minute's public count plus `max_pages` would exceed 4 (`intel/history.py:PUBLIC_BACKFILL_PAGES`). Investigation jobs of all teams together read at most 8 pages per minute (`intel/history.py:JOB_BACKFILL_PAGES`); a job past that waits with `last_error` `history_capacity`. Job pages never count toward the public 4 and public pages never count toward the job 8, so anonymous callers cannot take pages from jobs and jobs cannot close the route. Watch polling uses neither budget. Each backfill and job read keeps one checkpoint per account and kind, holding its lease and the one read per account per minute. A job read for a new account waits with `history_capacity` while 20,000 checkpoints are kept; it first deletes every checkpoint whose lease has ended and whose minute has passed, so finished reads never hold job reads shut (`intel/history.py:AccountHistory.claim_job_read`). Public backfills keep their cursors in at most 10,000 account and kind checkpoints; a backfill for a new account and kind that finds all 10,000 kept first removes one that holds no lease and whose minute has passed, an exhausted one before others and otherwise the one least recently advanced, together with its lease row, and is refused only when none can be removed, so the removed account's next backfill starts over without a cursor from its newest page while the pages and rows already archived for it stay (`intel/history.py:AccountHistory.backfill_account`).

Team investigation jobs (`/workspace-api/teams/<team>/investigation-jobs`) answer 503 `job_capacity` with `Retry-After: 60` and change nothing when a create, or a retry of a `failed` or `cancelled` job, would give the team more than 10 active jobs (`queued`, `running` or `retry_wait`; `intel/investigation_jobs.py:MAX_ACTIVE_JOBS`). A team retains at most 100 jobs (`intel/investigation_jobs.py:MAX_TEAM_JOBS`): a create at that limit first removes the team's oldest finished jobs (`completed`, `cancelled` or `failed`, by `created_ms`). Job bodies count against a 16 MiB share per team (`intel/investigation_jobs.py:MAX_TEAM_JOB_BYTES`) inside a 64 MiB bound across all teams (`intel/investigation_jobs.py:MAX_JOB_BYTES`). When a create or a running job's next page would take the team past its share, that team's own oldest finished jobs, by `created_ms`, are removed until it fits. When it would take all teams past the 64 MiB bound, the oldest finished jobs of any team are removed, oldest first by `updated_ms`, the time the job last became `completed`, `cancelled` or `failed`, until it fits. Every finished job is also removed 30 days after that time (`intel/investigation_jobs.py:RETENTION_MS`), oldest first and at most 1,000 per create or worker tick (`intel/investigation_jobs.py:MAX_EXPIRED_PER_WRITE`), whether or not its team returns; cancelling a job that is already `cancelled` does not change that time. `queued`, `running` and `retry_wait` jobs are never removed. If nothing finished is left to remove, the create answers `job_capacity`. Every fit check also keeps 10 bytes free for each active job counted against that bound (`intel/investigation_jobs.py:CAPACITY_STOP_BYTES`), the growth of a job that ends with `stop_reason` `job_capacity`, so that ending never takes usage past the team share or the 64 MiB bound; a retry of a `failed` or `cancelled` job that would leave less than that room after removals answers `job_capacity` and changes nothing. Each worker tick that takes a job first checks, before the archive, page budget and watch checks and before any provider read, that the team share and the 64 MiB bound have room for the larger of 2,048 bytes (`intel/investigation_jobs.py:MIN_JOB_ROOM`, more than the largest create) and the size of the job's last page that did not fit, removing finished jobs as above. With no room the job does not read the provider, and a page it read that does not fit is not added to the job. Either way the job stays `queued` with `last_error` `history_capacity` and `retry_at_ms` 60 seconds later and does not count it as a failed attempt. After three such waits in a row (`intel/investigation_jobs.py:MAX_CAPACITY_WAITS`), counting the first, the job ends `completed` with `stop_reason` `job_capacity` and `last_error` null, keeping the pages it already saved; a graph job ended this way answers `graph` null and keeps its retained transfers. A job whose final result does not fit ends the same way. A tick that finds room, or a saved page, starts the count again. A job ended this way cannot be retried. A job created before that 10-byte room was kept, whose ending finds no such room even after removing finished jobs as above, ends `failed` with `last_error` `job_capacity` and an unchanged body instead, keeping its saved pages; its retry answers `job_capacity` until that room exists. A storage error in a worker tick of `investigation-follow` is written to the service log and the worker tries again after its polling interval; with `--once` the command exits with the error. The count advances only when the job is due, which a provider cooldown can postpone, and a running worker takes it. While the worker runs, active jobs that lack that room therefore end after three waits whether or not the archive is also full, even when their team never returns, and as finished jobs they can then be removed. Provider, page budget and archive waits never count toward this limit and never end a job. While the archive, at the limits job pages use, has no room for one more page (`intel/history.py:MAX_ARCHIVE_PAGES`), for 100 more rows (`intel/history.py:MAX_ARCHIVE_ROWS`), the most one page holds, or for 4 MiB more bytes below the 112 MiB that pages and rows may use, the byte budget less its 16 MiB event share (`intel/history.py:MAX_ARCHIVE_BYTES`, `intel/history.py:EVENT_ARCHIVE_BYTES`, `intel/history.py:JOB_PAGE_BYTES`), twice the 2 MiB document limit (`intel/history.py:MAX_DOCUMENT_BYTES`) and so the most one accepted page and its rows take, no job reads the provider, even for a page the archive already holds, and each waits with `history_capacity`. Every job sees the same archive check, so no job takes a page to the job store while others wait on the archive. Another team's finished job can make room under the 64 MiB bound, but under the team share only the team's own finished jobs can. A removal deletes the job's rows and observations and releases their bytes in the same transaction, after which the job id answers 404 `not_found`. Removal is silent: it adds no audit entry and no job record, either for the team that held the job or for the team whose create or page caused it. A job yields to a due, unleased watched account only while the history worker heartbeat is at most 30 seconds old and its 30-second claim gate is open, so due watches between claim ticks do not delay job pages. A durable provider budget refusal keeps a job in `retry_wait` with `last_error` `provider_budget` until its retry time and does not count as a failed attempt. A yield is shown as `state` `queued` with `last_error` `watch_priority` and `retry_at_ms` 10 seconds later; after three yields in a row the next read does not yield, and a saved page sets `last_error` back to null. Other provider and archive budget waits show `last_error` `history_capacity` with `retry_at_ms` at least 60 seconds later.
